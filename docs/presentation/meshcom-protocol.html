Keine Transportsicherung — Flutnetzwerk-Prinzip
MeshCom nutzt ein Broadcast-Modell ohne klassische Transportsicherung (Handshakes, ACKs). Jede Nachricht wird von allen empfangenen Knoten gehört. Knoten mit aktiviertem Gateway leiten die Nachricht ins Internet weiter. Knoten mit aktiviertem Mesh wiederholen die Nachricht, um die Reichweite zu vergrößern.

Nachrichtenübertragung
Broadcast, DM & Wiederholung
Broadcast (Gruppe 262)
OE1ABC-12>262:{text}
Nachricht an Gruppe 262 wird von allen Knoten empfangen und weitergeleitet, wenn Mesh aktiviert ist. Weitergeleitet mit max_hop=4, dekrementiert bei jedem Relay.
Persönliche Nachricht (DM)
OE1ABC-12>OE9XYZ:Beispiel Text, 73{987
Direkt an OE9XYZ adressiert. Die {987 ist die 3-stellige ACK-Anfrage-Nummer (Nachrichtenzähler 0-999) ohne schließende Klammer.
Relaying & Wiederholung
📡 Mesh-Weiterleitung (Relay)
Jeder Knoten leitet empfangene Nachrichten einmal weiter (RING_STATUS_DONE = Fire-and-Forget). **Nicht weitergeleitet wird, wenn:**
  • Hop-Count = 0 (bereits dekrementiert vor dem Relay)
  • Schleife erkannt (eigenes Rufzeichen im Quellpfad)
  • Doppelte msg_id im Dedup-Ring (zirkulärer Puffer, kein Timeout)
  • Server-Flag gesetzt (Gateway hat bereits ins Internet weitergeleitet)
  • Nachrichtentyp nicht weiterleibbar (nur TEXT, POSITION, HEY)
  • Mesh deaktiviert (Knoten als Endpunkt konfiguriert)
🔁 Wiederholung durch Originator
**Nur der Ursprungsknoten wiederholt** TEXT-Nachrichten automatisch — bis zu **3 Versuche** im Abstand von ca. **40 Sekunden**. Nach 3 Versuchen stoppt die Wiederholung automatisch.
❌ Was cancelt das Relay?
Ein eingerichtetes Relay wird nicht storniert, selbst wenn ein anderer Knoten das Paket zuerst weitergeleitet. Grund: Das System muss ohne Topologie-Wissen funktionieren (Brückenknoten-Szenario). Stattdessen unterdrückt der Dedup-Ring neu eingereihte Relays.
✅ ACK-Behandlung
ACK-Frames werden nicht gemasht. Eine Nachricht mit ACK-Anfrage {NNN wird normal weitergeleitet, die ACK-Antwort :ackNNN aber direkt nur an den Sender gesendet (kein Mesh).
ACK-Format im Detail
ACK-Anfrage im DM (z. B. Nachricht 987)
Sender hängt an das Ende: {987
Diese Nummer ist der 3-stellige Nachrichtenzähler des Senders (0-999). Keine schließende Klammer!
ACK-Antwort vom Empfänger
Antwort wird mit Format :ack987 gesendet.
Bereich: 0-999, wird mit %03i formatiert (3-stellig, führende Nullen).
Gateway kompakter ACK
Gateways senden zusätzlich einen **12-Byte binären ACK** für Broadcast/Gruppe Nachrichten. Dieser ACK wird nicht weitergeleitet (nur Gateways versenden ihn).

🔌 LoRa TX-Puffer (Ring Buffer)
ringBuffer[MAX_RING] — zirkulärer Puffer mit 30 Slots
Slot 0: [Länge|Status|Type|MsgID|Payload...] Slot 1: [Länge|Status|Type|MsgID|Payload...] ... Slot 29: [Länge|Status|Type|MsgID|Payload...]
Status pro Slot:
• RING_STATUS_READY — bereit zum Senden
• RING_STATUS_DONE — bereits gesendet
• RING_STATUS_RESERVED — in Benutzung
🆔 Message ID Aufbau
32-bit msg_id Zusammensetzung:
((gw_id & 0x3FFFFF) << 10) | (counter & 0x3FF)
Top 22 Bits: Gateway-ID (von MAC abgeleitet)
Low 10 Bits: Nachrichtenzähler 0-999

⚠️ Wichtig: Zähler wraps bei 999, nicht 1024 (für {NNN} Format)
📊 Dedup-Ring
ringBufferLoraRX[MAX_DEDUP_RING] — speichert empfangene msg_ids

Funktionsweise:
✓ Verhindert doppelte Verarbeitung
✓ Zirkulärer Puffer ohne Timeout
✓ Alte Einträge werden beim Wrap-Around überschrieben
