# PR-Entwurf: DL-Gateway-Server auf dem Internet-Pfad wiederherstellen (Issue #1133)

> **Status: ENTWURF** (Stand 2026-09-06, Fork-Commit `b9934a4e`, Basis `upstream/dev` =
> `674413ce`). Ziel-Branch: icssw-org **DEV**. Noch **nicht** eingereicht, und noch **nicht**
> auf Hardware gegengemessen — siehe Abschnitt E.

Behebt [Issue #1133](https://github.com/icssw-org/MeshCom-Firmware/issues/1133): ein Heltec V3
und ein Heltec Wireless Tracker ignorieren beide `--gateway srv dl` seit dem Update auf 4.35s.
Der Bericht ist korrekt, und es handelt sich um eine Regression, nicht um eine
Konfigurationsfrage.

## A. Fehlerbild und Ursache

Die Einstellung geht **nicht** verloren. `--gateway srv dl` prüft den Ländercode, schreibt
`meshcom_settings.node_gwsrv`, ruft `save_settings()` auf, und `--info` zeigt anschließend
korrekt `GW server : DL` an. Der Wert überlebt auch den Neustart (ESP32: NVS-Schlüssel
`node_gwsrv`). Fehlerhaft ist ausschließlich die **Auswahl des Zielservers** beim
Verbindungsaufbau.

In `startMeshComUDP()` (`src/udp_functions.cpp`) wird das Ziel in zwei Zweigen bestimmt —
HAMNET (eigene 44er-Adresse oder `--sethamnet on`) und normales Internet. Als der
IT-Server eingeführt wurde, ist im **Internet-Zweig** der DL-Arm nicht ergänzt, sondern
**ersetzt** worden:

```c
      else   // Internet-Pfad
      {
-        if(memcmp(meshcom_settings.node_gwsrv, "DL", 2) == 0)
+        if(memcmp(meshcom_settings.node_gwsrv, "IT", 2) == 0)
         {
-          node_hostip = IPAddress(192, 68, 17, 26);      // DL-Server
+          WiFi.hostByName("meshcom.dig-italia.it", node_hostip);
         }
         else   // -> meshcom.oevsv.at
```

Damit ist das Literal `192.68.17.26` vollständig aus dem Baum verschwunden, und seither fällt
**jeder** Ländercode außer `IT` auf dem Internet-Pfad in den OE-Zweig. Ein DL-Knoten ohne
HAMNET-Adresse meldet sich also bei `meshcom.oevsv.at` an — genau die Beobachtung aus dem
Issue.

Wichtig für die Einordnung: `meshcom.hamnet.network` löst auf **192.68.17.26** auf, also auf
exakt das entfernte Literal. Es gab nie eine offene Frage, welcher Server für DL zuständig
ist; die Adresse war lediglich gelöscht.

**Warum es HAMNET nicht betrifft.** Der HAMNET-Zweig hat seinen DL-Arm durchgehend behalten
(`meshcom.hamnet.cloud` → `44.148.230.197`). Betroffen sind nur Knoten an einem gewöhnlichen
Internet-Anschluss — also der typische Heimnetz-Knoten, weshalb die Meldung aus genau dieser
Konstellation kam.

**Die nRF52-Seite war nie vollständig.** `NrfETH::startUDP()` und `NrfETH::startFIXUDP()`
(`src/nrf52/nrf_eth.cpp`) haben auf ihrem Internet-Zweig noch nie einen DL-Arm gehabt; CTY-01
hat dort seinerzeit nur die `IT`/`OE`-Unterscheidung nachgezogen. Ein DL-Gateway auf einem
RAK4631 mit Ethernet zeigt dasselbe Fehlbild, und zwar seit jeher.

## B. Was geändert wurde

Die Länder-/Transport-Matrix stand dreimal ausgeschrieben im Baum — einmal auf ESP32, zweimal
auf nRF52 — und ist genau deshalb auseinandergelaufen. Sie liegt jetzt einmal, als reine
Tabelle ohne Arduino-Abhängigkeit:

**Neu: `src/gwsrv_select.h`**

```c
struct GwSrvTarget { const char *host; uint8_t ip[4]; const char *path; };
static inline GwSrvTarget gwsrvSelect(const char *gwsrv, bool hamnet);
```

| Land | Transport | Host                     | Literal        | path     |
| ---- | --------- | ------------------------ | -------------- | -------- |
| OE   | inet      | `meshcom.oevsv.at`       | 89.185.97.38   | `inet`   |
| OE   | hamnet    | —                        | 44.143.8.143   | `hamnet` |
| DL   | inet      | `meshcom.hamnet.network` | 192.68.17.26   | `inet`   |
| DL   | hamnet    | `meshcom.hamnet.cloud`   | 44.148.230.197 | `hamnet` |
| IT   | beide     | `meshcom.dig-italia.it`  | 145.239.75.155 | `inet`   |

Die Tabelle liefert bewusst **Name und Literal zugleich**: der ESP32-Pfad hat einen
asynchronen DNS-Resolver und braucht den Namen, der nRF52-Ethernet-Pfad hat keinen und braucht
die feste IP. Bisher standen beide Werte an getrennten Stellen; damit konnten dieselben
Einstellungen je nach Board auf unterschiedlichen Servern landen. Jetzt nicht mehr.

`IT` liefert auf beiden Transporten `path = "inet"`, weil es keinen IT-HAMNET-Server gibt —
das entspricht dem bisherigen Verhalten samt des vorhandenen Kommentars.

**Geändert: `src/udp_functions.cpp`** — in `startMeshComUDP()` ersetzen die beiden
Länderketten einen einzigen Aufruf. Das äußere `if (HAMNET) / else` bleibt bestehen, weil die
**NTP-Auswahl** darin strukturell unterschiedlich ist und von dieser Änderung unberührt bleibt
(einschließlich der `node_ip[1] == 143`-Unterscheidung). `[GW];srv`-Marker, `wifiDnsStart()`
und der `bWIFIAP`-Zweig sind unverändert.

**Geändert: `src/nrf52/nrf_eth.cpp`** — dieselbe Ersetzung in `startUDP()` und
`startFIXUDP()`; beide erhalten dabei den DL-Arm, den sie nie hatten. Die jeweils
verzweigungsabhängige NTP-Zuweisung fällt auf einen `path`-gesteuerten Ternär zusammen. Die
Äquivalenz ist zellenweise geprüft:

| Fall               | neuer `path` | NTP neu       | NTP bisher                 |
| ------------------ | ------------ | ------------- | -------------------------- |
| hamnet, IT         | `inet`       | 162.159.200.1 | 162.159.200.1 (IT-Arm)     |
| hamnet, DL         | `hamnet`     | 44.143.0.9    | 44.143.0.9 (DL-Arm)        |
| hamnet, OE         | `hamnet`     | 44.143.0.9    | 44.143.0.9 (else-Arm)      |
| Internet, beliebig | `inet`       | 162.159.200.1 | 162.159.200.1 (beide Arme) |

Die `[GW];srv`-Marker-Zeile in `startUDP()` bleibt unangetastet. In `startFIXUDP()` wird
bewusst **kein** Marker ergänzt — diese Lücke ist bekannt und gehört nicht in diesen PR.

**Geändert: `src/command_functions.cpp`** — nur Kommentare, siehe Abschnitt C.

## C. Vorbereitete Plätze für weitere Länder

Auf Wunsch aus dem Fork-Betrieb enthält `gwsrv_select.h` auskommentierte Arme für `HB`
(Schweiz) und `US` (USA), jeweils für HAMNET und Internet, samt Checkliste am Dateiende.
`command_functions.cpp` enthält die passende, fertig formulierte Ersatzzeile für die
Allow-Liste des `--gateway srv`-Kommandos.

Beide Stellen müssen aktiviert werden: die Allow-Liste wird **zuerst** geprüft, ein
freigeschalteter Arm allein bliebe also unerreichbar. Der Ländercode ist wegen
`memcmp(.., 2)` und `node_gwsrv[3]` exakt zweistellig und großgeschrieben; ein längerer Code
wäre eine Flash-Format-Änderung.

Wer einen Server einträgt, füllt Hostname **und** Literal aus — die Testsuite prüft beide
gemeinsam, damit ein halb ausgefüllter Eintrag nicht durchrutscht.

## D. Absicherung

- **Neue native Regressionssuite** `test/test_gwsrv_select/` (9 Fälle, in `env:native`
  registriert): jede Zelle der Matrix mit Host und Literal, der leere Default, ein unbekannter
  Ländercode, und eine Schleife über alle Kombinationen. Die Suite wurde **gegen das kaputte
  Verhalten zuerst geschrieben** und lief rot auf genau der DL-Internet-Zelle
  (`Expected 'meshcom.hamnet.network' Was 'meshcom.oevsv.at'`), bevor der Arm ergänzt wurde.
- Gesamte native Suite: **284/284**.
- Builds: `wiscore_rak4631` (mit `-Werror`), `heltec_wifi_lora_32_V3` und
  `heltec_wireless_tracker` — also beide im Issue genannten Boards.
- Baumweite Prüfung: **jede** Serveradresse in `src/` steht jetzt in genau einer Datei.
- Keine Änderung an `FLASH_VERSION` oder `FLASH_STRUCT_VERSION` — Knoteneinstellungen bleiben
  erhalten, und ein Knoten mit gespeichertem `DL` erreicht nach dem Update einfach wieder den
  richtigen Server.

## E. Offen vor der Einreichung

1. ~~**Hardware-Gegenprobe fehlt.**~~ **Erledigt 2026-09-06, beide Plattformen.** `DK5EN-93`
   (Heltec V3, WLAN, Internet-Pfad): `[GW];srv;OE;host;meshcom.oevsv.at;path;inet` →
   nach `--gateway srv dl` → `[GW];srv;DL;host;meshcom.hamnet.network;path;inet`.
   `DK5EN-90` (RAK4631, W5100S-Ethernet, DHCP-Pfad):
   `[GW];srv;OE;host;89.185.97.38;path;inet` → `[GW];srv;DL;host;192.68.17.26;path;inet`.
   Beide Knoten liefen mit `Gateway off`; der gesamte KEEP-Verkehr ist auf beiden
   Plattformen `bGATEWAY`-gegated, auf dem ESP32 zusätzlich per `--srvip 192.0.2.1` auf eine
   Senke umgelenkt — es hat also kein Paket den echten DL-Server erreicht. Beide Knoten
   danach auf OE zurückgestellt. Details in `docs/bench-country-servers.md`.

2. **Bestätigung durch die DL-Serverbetreiber**, dass `meshcom.hamnet.network` der
   vorgesehene Internet-Endpunkt ist und nicht nur historisch der Dashboard-Host. Die
   DNS-Auflösung stützt es, eine Bestätigung wäre sauberer.
3. **Schnittfrage:** Der PR enthält mit `test/test_gwsrv_select/` und der
   `platformio.ini`-Zeile Test-Anteile. Falls upstream reine Firmware bevorzugt, lassen sich
   beide herausnehmen — die Suite ist die einzige Absicherung der Matrix und bliebe dann im
   Fork.
