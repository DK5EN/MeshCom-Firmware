# Hey storm 2026-10-17 - N1WBV-6

## Verdict

N1WBV-6 caused the hey storm on 17 Oct 2026. The pattern matches the known 32-bit millis() overflow bug
(49.71 days of uptime). The node never reports its uptime, so the overflow is inferred, not proven.

| Location | Rhode Island, US (41.635, -71.0058)          |
| Hardware | HELTEC V3                                    |
| Firmware | 4.35p                                        |
| Role     | Gateway (gw:1), seen via INTERLINK, hub `oe` |

The 4.35p letter alone does not say whether the build has the millis() fix (upstream took it on
2026-08-27, mid-cycle).

## Evidence

- 14,557 hey frames from this one sender in the 11:00-12:00 UTC hour (13:00 Vienna). That accounts for
  the excess over the normal ~6.5k/h and the 20,671 on the chart.
- Normal behaviour before: one hey every 900 s (10:31:52, 10:46:52, 11:01:52 UTC).
- The burst starts on the 11:16:52 UTC beacon boundary and runs until about 11:33-11:35 UTC, roughly
  17-19 minutes. Each frame has a fresh `msg_id`, so these are newly built frames, not replays.
- The pos beacon went to one frame every 30 s from about 11:03 to 11:30:00 UTC, then back to normal at
  12:00:38. Same failure family as the pos rapid-fire in the findings doc.
- Hour bars after 14:00 Vienna are back to normal.

## Did the node report for the 49.7-day turnover?

No uptime or millis value is carried in hey or pos frames, so it cannot be read directly. Indirect
evidence:

- Storm start 17 Oct 11:16:52 UTC minus 2^32 ms (49.71 d) = 28 Aug 2026, about 18:14 UTC.
- The node's pos telemetry (weather values) shows beacons every 30m15s up to 18:06:45 UTC on 28 Aug,
  then a 51-minute gap to 18:57:52 UTC (one frame missed) and a shifted timing phase afterwards. That
  is a restart inside the predicted window.
- Raw frames from 28 Aug no longer exist (log retention is 20 days), so the reboot is read from the
  telemetry series, not from wire frames.

## Constant stream over the last 50 days?

Yes. Source: stored telemetry for N1WBV-6 (carried by its pos frames), 28 Aug to 17 Oct.

- Median interval 30.5 minutes, about 47 pos frames per day on every day in the window.
- Real gap: 7 Oct, 6.6 hours from 10:05 UTC. It coincides with a dip in the hub's gateway heartbeat for
  this node (about 79% that day), so the node was likely offline.
- Minor gaps: 91-121 minutes around 26-28 Aug, and a handful of 61-minute gaps (about two missed
  frames each).
- Telemetry for this node only starts 14 Aug and has a hole from 17 to 25 Aug. That is outside the
  50-day window.

## Storm detector

The existing filters cannot catch this: storm frames carry fresh `msg_id`s, so `HeyDedupeFilter`
(`proxy/src/interlink/heyDedupe.ts`) and `PosTwinFilter` treat them as distinct. The detector must be
rate-based per sender.

Proposed shape:

- Pure leaf module like `posTwinFilter.ts`, with the same off / observe / drop modes, called from
  `ingest.ts` before storage.
- Normal cadence is 1 hey per 15 min and 1 pos per 30 min; storms ran at 8-18 frames per second, so a
  threshold has orders of magnitude of margin.
- Flagged sender: drop frames until it is quiet again.
- The raw wire line in `interlink.log` is written before the filters run and stays.
- Side effect: the Activity chart would no longer show true wire volume, so dropped frames need their
  own counter.

Open decision: drop everything from a flagged sender, or only the type that stormed. Recommended: only
the stormed type, so normal messages and telemetry still get through.

## Firmware guard: updated nodes stop relaying for affected builds

Idea (owner, 2026-10-17): once an updated node knows a neighbour runs an affected build, it
refuses to relay that neighbour's frames. That puts pressure on the operator to update without a
central ban, and it stops a storm from spreading across the mesh before it reaches a gateway.

### What makes it feasible

- Every RF frame already carries the source's firmware: a version byte (35 = 4.35) and a sub-letter
  (`aprs_functions.cpp:494`, `:517`; encoder `:1121-1131`). No neighbour table and no pos frame is
  needed, and the version is known from the first frame on.
- The mechanism already exists. Since `c5e5d156` (2026-05-05, 4.35p) the decoder discards every
  packet with a source version below 4.35a (`aprs_functions.cpp:533`): it is not shown, relayed or
  uploaded. The guard moves that cutoff, and should only skip relaying instead of discarding.

### Which builds the cutoff can name

The fw string does not record the build date. The millis() fix is `0cac4aea` (2026-08-27), in the
middle of the 4.35p cycle. Active pos senders over the last 7 days (prod wire, 2026-10-10..17,
2293 senders):

| Version       | Affected?                                       | Nodes | Share | Of which gateways |
| ------------- | ----------------------------------------------- | ----- | ----- | ----------------- |
| 4.35a - 4.35o | always                                          | 278   | 12.1% | 132               |
| 4.35p         | builds before 2026-08-27 only; can't tell which | 537   | 23.4% | 251               |
| 4.35s and up  | fixed                                           | 1478  | 64.5% | -                 |

A cutoff at 4.35p would cut off 35% of the network, including about 380 gateways, most of them
on fixed 4.35p builds. So the version cutoff can only safely name 4.35a-4.35o.

### Proposed shape (two layers)

1. **Behaviour guard (always on, catches every build).** In the relay path
   (`lora_functions.cpp` ~2420-2490), keep a small per-source table (call + msg_id upper22) and
   refuse to relay a source that originates HEY or POS faster than any stock firmware path can:
   HEY more often than once per 30 s, POS more often than once per 30 s sustained. The msg_id
   counter is a second signal: a low-10 jump of about 100 or more between two consecutive frames
   from one source means it is producing frames at loop rate. This catches the millis() storm on
   4.35p builds that the version cutoff cannot name, as well as modified builds and future timer
   bugs. Release the source as soon as it has been quiet for a few minutes.
2. **Version guard (relay only, scoped).** Do not relay HEY and POS from sources reporting
   4.35a-4.35o. Still deliver and relay text messages: operator traffic, including emergency
   traffic, must not be cut off over a beacon bug. Behind a setting, default on in the next
   release, so that an operator in an area served only by old nodes can switch it off.

### Risks and open points

- **Partition.** 132 of the 278 old nodes are gateways, and some are the only digipeater in their
  area (for example DH8OH-99 "Digipeater", 4.35i). If updated nodes stop relaying their beacons,
  their users disappear from the map and the hub, not just the broken device. Graduated rollout:
  behaviour guard first, version guard one release later.
- **Spoofing.** The fw byte is self-reported and unauthenticated. A frame forged with someone
  else's call and an old version would get the victim blocked. Key the decision on call + msg_id
  upper22 (the MAC slice) rather than on the call alone.
- **Updating has to free the node at once.** The version is in every frame, so the first frame
  after the update releases it. No waiting for the next pos (first pos about 30 min after boot).
- **Gateways are not covered.** A guard on the relay path does not stop an old gateway's own
  uplink. That remains a hub/server decision (and the mcmap storm detector above).
- **Measure first.** Run the behaviour guard in count-only mode for one release cycle and read the
  counters before it drops anything, as with the server-side detector.

### Server-side ban: HB4LO-2 and DL1ISG-8

Both went silent on 2026-10-05 (last own frame 08:52Z and 14:04Z). The data does not show a
version-based ban. Other nodes on the same builds (4.35p: DC2SK-12; 4.35f: OE3RDB-2, IZ5YYF-12)
stayed on the feed through 10-17. The 81 senders last seen on 10-04/05 are mostly 4.40a (44),
which is normal churn. Neither station appears as a relay in anyone's path after 10-05. A
per-callsign block on the hub, or the devices simply being switched off, both fit the data; ask
the hub admin.
