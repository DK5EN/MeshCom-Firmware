# Production-locked settings: specification

Status: implemented (wave W4, `src/prod_lock.h` and its call sites); this document describes the implementation, the audit findings are kept as the reason for it. Audited against `fork-dev` (2026-10-18). Deutsch zuerst, English second; both halves carry the same content.

# Deutsch

## BLUF

- Produktions-Builds (ohne `-DINSTRUMENT_ENABLED=1`) bekommen für zehn Protokoll-Tuning-Einstellungen feste Werte, die keine Oberfläche mehr ändern kann. INSTRUMENT-Builds ändern sich nicht.
- Gesperrt (fester Wert = heutiger Default): `--nbrrelay` (off), `--nbrsym` (on), `--nbrreport` (auto), Max-Hop für Positionen (2), `--shortpath` (off), `--pingtime` und `--pingmax`, die vier `--spec*`-Parameter (432.0 / 434.0 / 0.025 / 2048). Zusätzlich in Produktion: `--stor on` (Mailbox-Ankündigung) wird abgelehnt, `node_stor` wird 0. In **allen** Builds (auch INSTRUMENT): `--autoupdate auto` wird nie angenommen, ein gespeichertes `node_autoupd` 2 wird 1.
- Einstellbar mit Begrenzung: Max-Hop Text 1..6, `--postime` 300..86400, `--ptime` 5..120, TX-Leistung im Board-Bereich. Nicht gesperrt: SF, Bandbreite, Coding Rate, Gateway, Mesh, Via, Hamnet/Inet/Auto.
- Beim Boot überschreibt ein Produktions-Build gespeicherte Werte der gesperrten Einstellungen mit dem festen Wert und repariert so bereits verstellte Knoten.
- Das Audit zeigt: Die Konsole ist nicht die einzige Tür. Fast alle Wege münden in `commandAction()` (dort sitzt das Tor, `prodLockRefuses()`; Ablehnung `[ERR];locked;<name>`), aber fünf Wege schreiben direkt in die Einstellungen und umgehen jedes Kommando: LoRa `{SET}` (`prodLockSetHop()`), Config-JSON-Import (`sub_config_upload()` ruft `prodLockNormalise()` vor `save_settings()`), der nRF52-BLE-Settings-Blob, der Boot-Load (beide rufen `prodLockNormalise()`) und die Web-Spektrum-Seite (schreibt keine `node_spec*` mehr).
- Beim Audit gefundene Fehler sind mit dieser Arbeit behoben, einschließlich der Passwortfrage bei `{SET}` (entschieden, siehe Fragen): `{SET}` setzt Hop-Limits im ganzen Netz (jetzt Text-Hop 1..6, Position ignoriert), `--ptime` hatte einen falschen Fallback (30 Stunden), `--postime` hatte einen toten Zweig, `--pingtime` erlaubte Werte, die die Hauptschleife ignoriert (Details im Abschnitt "Beim Audit gefundene Fehler").

## Geltungsbereich und Schalter

- "Produktion" bedeutet: `INSTRUMENT_ENABLED` ist 0. Das ist der Default (`src/instrument.h:34-39`); keine Build-Umgebung setzt es auf 1 (`src/configuration_global.h:235-250`). Der Auslieferungs-Build braucht also keine Änderung.
- Umsetzung: kein Makro, sondern der Header `src/prod_lock.h` (rein, ohne Arduino). Die Firmware-Aufrufstellen übergeben `INSTRUMENT_ENABLED != 0` als Parameter `instrument`.
- Hosttests: `src/instrument.h:36-38` erzwingt `INSTRUMENT_ENABLED 0` auf Native/Host. Deshalb nehmen alle Funktionen in `src/prod_lock.h` `instrument` als Parameter; der Hosttest (`test/test_prod_lock`, `pio test -e native_prod_lock`) prüft beide Werte, und nur die Firmware setzt `INSTRUMENT_ENABLED != 0` ein.
- `MC_DIAG` (Default 1) bleibt unabhängig. Es schaltet nur, ob die `--spec*`-Kommandos kompiliert werden (`src/command_functions.cpp:5457-5552`); gesperrt werden sie zusätzlich in Produktion.
- Regeln für **alle** Builds (auch INSTRUMENT): `--autoupdate auto` wird nie gesetzt (Wert 2 des Schemas), ein gespeichertes `node_autoupd` 2 wird beim Laden 1 (nicht auf nRF52, dort gibt es kein AU); Telemetrie-, Positions- und Ping-Werte bleiben in den Bereichen ihrer Setter.

## Wo die Sperre sitzen muss

Drei Einstiegspunkte in `src/prod_lock.h` (rein, ohne Arduino, hosttestbar; Parameter `instrument`): `prodLockRefuses()` (Kommando-Tor), `prodLockNormalise()` (jeder Weg, der die Struktur ohne Kommando schreibt) und `prodLockSetHop()` / `prodLockSetPosAllowed()` (LoRa `{SET}`), dazu die Boot-Reparatur.

**1. Das Kommando-Tor in `commandAction(char*, bool)`** (`src/command_functions.cpp:822`), unmittelbar vor `toggleApply()` (`:879`). Diese Funktion ist der Engpass für Konsole, TCP-Konsole 2323, Web `manualcommand`, die Web-Setup-Parameter, BLE-Text, RM1, T-Deck-Tipptext und alle `commandAction()`-Aufrufe im Code. Der äußere Wrapper `commandAction(char*, int, bool)` (`:670`) zerlegt verkettete Zeilen (`--a --b`) und ruft die innere Funktion je Teilkommando auf; das Tor muss in der inneren Funktion sitzen, sonst schlüpft ein Teilkommando durch.

- `prodLockRefuses(const char *cmd, bool instrument)` prüft das erste Token nach `--` exakt (Regel von `commandMatches`) gegen `nbrrelay`, `nbrsym`, `nbrreport`, `shortpath`, `pingtime`, `pingmax`, `specstart`, `specend`, `specstep`, `specsamples`. Zusätzlich: in allen Builds `autoupdate auto`, in Produktion `stor on`. Liefert den Namen für die Meldung oder `nullptr`.
- Bei Treffer: Ausgabe `[ERR];locked;<name>` (Serial; bei BLE zusätzlich als Antwortzeile über `addBLECommandBack()`), keine Änderung, `return`. Der Aufruf lautet `prodLockRefuses(msg_text+2, INSTRUMENT_ENABLED != 0)` und steht vor `toggleApply()`.
- Die Wertbegrenzungen für `--postime`, `--ptime`, `--maxhop` und `--txpower` bleiben in ihren Parsern, rufen aber dieselben Klemm-Funktionen (`prodClampPostime()`, `prodClampPtime()`) auf, die auch die Normalisierung benutzt. Eine Quelle für die Grenzen.

**2. Die Normalisierung `prodLockNormalise(S &s, bool instrument, bool hasAutoUpdate)`** in `src/prod_lock.h` (Template über den Strukturtyp, damit sie auf dem Host gegen eine Attrappe läuft; `hasAutoUpdate` ist auf nRF52 `false`). Sie ist idempotent und gibt die Zahl der geänderten Felder zurück. In allen Builds: `node_autoupd` 2 wird 1, `node_postime` 1..299 wird 300 und über 86400 wird 86400, `node_parm_time` kommt nach 5..120 (0 wird 15), `node_pingmax` über 5 wird 5, `node_pingtime` außerhalb 0 / 30..300 wird 60. Nur in Produktion zusätzlich:

- löscht in `node_sset4` genau die Bits 0x3B00 (0x0100, 0x0200, 0x0800, 0x1000, 0x2000) und in `node_sset` genau Bit 0x0400; `0x0400` in `node_sset4` (`--nbrdebug`) bleibt unberührt;
- lässt `node_pingmax` 0 oder 1..5 stehen (0 und 5 sind gleichwertig) und setzt `node_pingtime` auf `node_pingcall[0] ? PING_INTERVAL : 0`;
- setzt die vier Spektrumfelder auf 432.0 / 434.0 / 0.025 / 2048;
- setzt `max_hop_pos` auf `MAX_HOP_POS_DEFAULT`;
- setzt `node_stor` auf 0. `max_hop_text` (1..6) bleibt bei der bestehenden Regel `maxHopTextSanitize()`.

Aufrufstellen der Normalisierung (alle Wege, die an `commandAction()` vorbei schreiben):

Verworfene Alternativen:

- Normalisierung in `save_settings()`: Beim Laden wird `save_settings()` auf einer halb geladenen Struktur gefährlich (`src/esp32/esp32_flash.cpp:546-573` beschreibt genau diesen Schaden). Die Kopplung `pingtime` = f(`pingcall`) würde dann gültige Werte überschreiben.
- Je Setter ein `#if`: zehn Stellen, die ein künftiges Kommando vergessen kann. Das Tor mit Namensliste plus der Quelltext-Scan im Testplan schließt das.
- Die vier `--spec*`-Kommandos in Produktion herauskompilieren: möglich, löst aber Blob, Import und Boot nicht; die Normalisierung braucht ohnehin den festen Wert.

Boot-Verhalten: In Produktion wird nur beim Abweichen geschrieben (ein Flash-Schreibvorgang, danach idempotent). Auf bereits verstellten Knoten wirkt die Reparatur mit dem ersten Boot des neuen Images. Danach ist auch der Laufzeitzustand (`bNBRRELAY` usw.) konsistent mit den Bits, denn die Flags werden nach dem Laden aus den Bits abgeleitet.

Zusätzlich im Web: Die Spektrum-Seite schreibt nicht mehr in `meshcom_settings`, sondern rechnet mit lokalen Variablen (siehe Fehlerliste); sonst brach sie bei 868 MHz den festen Wert auf `863/870/0.100`.

## Beim Audit gefundene Fehler

Stand der Umsetzung: Fehler 1 ist im Bereich behoben (Text-Hop 1..6, Position nur in INSTRUMENT), die Passwortfrage ist entschieden (ohne Passwort, genehmigte Sicherheitsausnahme). Die Fehler 2 bis 7 und 10 sind behoben, 8 und 9 durch `prodLockNormalise()` und die Bereichsanpassung abgedeckt.

1. **`{SET}` ist ohne Passwort und mit zu weitem Bereich** (`src/loop_functions.cpp:2516-2550`). Der Zweig steht in `sendDisplayText()` neben `{MCP}`; nur `{MCP}` prüft `cpasswd` (`:2443-2470`), `{SET}` prüft nichts. Er wird für Frames ausgeführt, die nicht an den Knoten selbst adressiert sind (`src/lora_functions.cpp:2083-2090`) und wird nicht vom Relay ausgenommen (anders als `{ping}`/`{pong}` bleibt `bMeshDestination` unverändert, `:2083-2090`). Wirkung: Ein einziger Rundspruch `{SET}n;m;` setzt bei jedem Knoten in Funkreichweite und den Relays dahinter das persistente `max_hop_text` auf 0..7 (außerhalb von 1..6, siehe `src/maxhop.h:17-18`) und das Positions-Hop-Limit auf 0..7 bis zum Reboot. Mit 0 verlässt keine Nachricht den Knoten, mit 7 flutet er. Behebung: Text-Hop nur 1..6 annehmen, Positionsfeld in Produktion ignorieren; die Passwortfrage (jeder Sender vs. nur Gateway/Betreiber) ist entschieden: kein Passwort, siehe Fragen.
2. **`--ptime`-Fallback falsch** (`src/command_functions.cpp:6702-6713`, Boot-Seite `src/esp32/esp32_main.cpp:4724-4727`, `src/nrf52/nrf52_main.cpp:2237-2241`). Der Bereich ist 5..120 Minuten, der Fallback `TELEMETRY_INTERVAL` ist `30 * 60` (`configuration_global.h:279`, ein Sekundenwert mit der Kommentarangabe "Minuten"). Der Timer rechnet danach `* 1000 * 60` (`esp32_main.cpp:4730`): 1800 Minuten = 30 Stunden. Ein Tippfehler wie `--ptime 200` speichert 1800 und schaltet die Telemetrie praktisch ab; der gespeicherte Wert 1800 ist selbst außerhalb 5..120 und wird jeden Boot erneut auf 1800 Minuten abgebildet. Der Config-Import erlaubt 1800 sogar ausdrücklich (`config_json.h:323`: 0..1800). Behebung: auf die nächste Grenze begrenzen (oder 15, den echten Default `meshcom_settings.h:139`), Fallback-Konstante in Minuten.
3. **`--postime`: toter Zweig und falscher Wiedereinstieg** (`src/command_functions.cpp:1119-1139`). Nach der Untergrenze 300 ist `node_postime > 0` immer wahr; der `else`-Zweig `posinfo_interval = POSINFO_INTERVAL` (`:1134-1135`) ist unerreichbar. Folge: `--postime 0` ergibt 300 s statt Default 1800 s, und `--postime abc` (der `sscanf`-Fehlschlag lässt den alten Wert 0 stehen) setzt auf 300 s, also sechsfache Positions-Airtime. Der Kommentar sagt "minimum 3 Minuten", der Code 5. Behebung: 0 bedeutet Default (Zweig bekommt wieder einen Sinn), nicht parsebare Eingabe wird abgelehnt.
4. **Mehrere Setter ohne Parse-Prüfung**: `--postime`, `--ptime`, `--pingtime`, `--pingmax` benutzen rohes `sscanf` (`:1121`, `:6704`, `:3762`, `:3811`). Eine Nicht-Zahl bleibt als 0 oder als alter Wert stehen und wird dann begrenzt oder auf den Fallback gesetzt. Die anderen Setter lehnen Nicht-Zahlen ab (`cmdArgNotNumber`, `:736-749`).
5. **`--pingtime` erlaubt Werte, die die Hauptschleife ignoriert**: Setter-Untergrenze 15 (`:3764`), aber die Schleifen senden erst bei `node_pingtime > 29` (`src/esp32/esp32_main.cpp:5109`, `src/nrf52/nrf52_main.cpp:2681`). 15..29 wird gespeichert, aber nie gepingt, und schaltet trotzdem HEY und Nachbarbericht ab (`loop_functions.cpp:5436`, `5528`).
6. **`--pingmax max` widerspricht `PING_MAX`**: setzt 100 (`:3800-3806`), die Obergrenze ist 5 (`:3813`), der Import erlaubt 0..100. Außerdem setzt `--pingmax 7` auf 5 zurück statt zu begrenzen.
7. **Spektrum-Einstellungen sind wirkungslos und werden überschrieben**: `--spectrum` benutzt feste Werte (`src/spectral_scan.cpp:138-166`), die Webseite setzt `node_spec*` bei jedem Aufruf auf 432/434/0.025/2048 oder bei > 860 MHz auf 863/870/0.100 (`web_functions.cpp:3927-3938`) und speichert diese beim nächsten `save_settings()` mit. Die Kommando-Bereiche (430..439 und 869.4..869.65, `command_functions.cpp:5463-5500`) passen nicht zu den Werten der Seite. `--specsamples` meldet die Einheit "MHz" (`:5544`).
8. **nRF52-BLE-Blob ohne jede Prüfung** (`src/nrf52/ble_settings_v1.cpp:229-420`, angewendet in `src/nrf52/nrf52_ble.cpp:514-552`): Jedes Feld, auch `node_sset`, `node_sset4`, `node_power`, `max_hop_text`, `max_hop_pos`, die Ping- und Spektrumfelder, wird übernommen und gespeichert. Der Boot prüft später nur Funkparameter und `max_hop_text`.
9. **Config-Import hat weite Bereiche** (`src/config_json.h`): postime 0..86400, ptime 0..1800, pingtime 0..86400, pingmax 0..100, Spektrum 0..1e9. Umsetzung: `node_autoupd` 0..2 (2 wird zu 1 normalisiert) und die Spektrumfelder in den Setter-Bereichen (Start/Ende 400..960, Schritt 0.01..2.0, Samples 500..2048); ptime, pingtime und pingmax behalten absichtlich die alten weiten Bereiche, damit eine Sicherung eines älteren Builds importierbar bleibt, `prodLockNormalise()` repariert die Werte vor dem Speichern.
10. **Kosmetisch**: Die Hilfetexte nannten für `--postime 99` / `--ptime 99` keine Bereiche. Behoben: `--postime 300..86400` und `--ptime 5..120` stehen in `--help` (`help_parity_lint` bleibt grün).

# English

## BLUF

- Production builds (without `-DINSTRUMENT_ENABLED=1`) get fixed values for ten protocol-tuning settings that no surface can change any more. INSTRUMENT builds are unchanged.
- Locked (fixed value = today's default): `--nbrrelay` (off), `--nbrsym` (on), `--nbrreport` (auto), max hop for position (2), `--shortpath` (off), `--pingtime` and `--pingmax`, the four `--spec*` parameters (432.0 / 434.0 / 0.025 / 2048). Additionally in production: `--stor on` (mailbox announcement) is refused and `node_stor` becomes 0. In **all** builds (INSTRUMENT too): `--autoupdate auto` is never accepted and a stored `node_autoupd` 2 becomes 1.
- Settable with a clamp: max hop text 1..6, `--postime` 300..86400, `--ptime` 5..120, TX power within the board range. Not locked: SF, bandwidth, coding rate, gateway, mesh, via, hamnet/inet/auto.
- At boot a production build overwrites stored values of locked settings with the fixed value and so repairs nodes that are already broken.
- The audit shows the console is not the only door. Almost every path ends in `commandAction()` (that is where the gate sits, `prodLockRefuses()`; refusal `[ERR];locked;<name>`), but five paths write into the settings directly and bypass every command: LoRa `{SET}` (`prodLockSetHop()`), config JSON import (`sub_config_upload()` calls `prodLockNormalise()` before `save_settings()`), the nRF52 BLE settings blob and the boot load (both call `prodLockNormalise()`), and the web spectrum page (no longer writes `node_spec*`).
- Defects found while auditing are fixed with this work, including the password question for `{SET}` (decided, see questions): `{SET}` changes hop limits across the mesh (now text hop 1..6, position ignored), `--ptime` had a wrong fallback (30 hours), `--postime` had a dead branch, `--pingtime` accepted values the main loop ignores (details in "Bugs found while auditing").

## Scope and switch

- "Production" means `INSTRUMENT_ENABLED` is 0. That is the default (`src/instrument.h:34-39`); no build environment sets it to 1 (`src/configuration_global.h:235-250`). The shipping build needs no change.
- Implementation: no macro, the header `src/prod_lock.h` (pure, no Arduino). The firmware call sites pass `INSTRUMENT_ENABLED != 0` as the parameter `instrument`.
- Host tests: `src/instrument.h:36-38` forces `INSTRUMENT_ENABLED 0` on native/host. Every function in `src/prod_lock.h` therefore takes `instrument` as a parameter; the host test (`test/test_prod_lock`, `pio test -e native_prod_lock`) exercises both values and only the firmware passes `INSTRUMENT_ENABLED != 0`.
- `MC_DIAG` (default 1) stays independent. It only decides whether the `--spec*` commands are compiled (`src/command_functions.cpp:5457-5552`); in production they are additionally locked.
- Rules that hold in **all** builds (INSTRUMENT too): `--autoupdate auto` is never set (value 2 of the schema), a stored `node_autoupd` 2 becomes 1 on load (not on nRF52, which has no AU); telemetry, position and ping values stay inside the ranges of their setters.

3. Only when `MC_DIAG` is on (default; only E22_XML builds without it). On nRF52 the four fields are pure RAM state (`src/meshcom_settings_runtime.h`).
4. `{SET}` sets `max_hop_pos` in RAM (`src/loop_functions.cpp`); the nRF52 blob copies the field unchecked (`src/nrf52/ble_settings_v1.cpp:419`). Boot resets it to the default (`src/esp32/esp32_main.cpp:1531`, `src/nrf52/nrf52_main.cpp:744`). Implementation: `{SET}` takes the position field only in INSTRUMENT builds (`prodLockSetPosAllowed()`); `prodLockNormalise()` sets `max_hop_pos` to the default in production.
5. The blob writes `max_hop_text` unchecked (`ble_settings_v1.cpp:418`). Implementation: `applyPendingBleSettings()` then calls `maxHopTextSanitize()` and `prodLockNormalise()` before saving.
6. See bug list: no password (approved security exception, 2026-10-18). Range in production 1..6 (`prodLockSetHop()`), in INSTRUMENT builds 0..7.
7. Blob and import do not check `node_power` against the board range until the next boot.

On the columns without a write site of their own:

- Web `manualcommand` (`src/web_functions/web_setup.cpp:31-37`) hands any string to `commandAction()` (`&&` becomes `--`).
- The web setup parameters `maxhop` and `txpower` also run through `commandAction()` (`web_setup.cpp:135-173`). Postime, ptime, ping, nbr and shortpath have no named parameter there.
- RM1 can only write toggles (`gps track display led gateway mesh`), `txpower`, `setout`, `chgled`, `name`, `atxt`, `pos`, `upd` (`src/rm_commands.h:36-58`), all through fixed console lines (`src/rm_runtime.cpp:109-130`, `src/rm_exec_write.cpp:58-63`). `maxhop` is read-only. No locked setting is reachable.
- T-Deck UI: the setup form writes callsign, name, position, mesh, webserver and the like through `commandAction()` (`src/t-deck/event_functions.cpp:380-644`). There is no widget for a locked setting. Text typed on the keyboard that starts with `-` goes through `sendMessage()` into `commandAction()` (`src/loop_functions.cpp:4064-4072`).

## Where the lock must sit

Three entry points in `src/prod_lock.h` (pure, no Arduino, host-testable; parameter `instrument`): `prodLockRefuses()` (command gate), `prodLockNormalise()` (every path that writes the struct without a command) and `prodLockSetHop()` / `prodLockSetPosAllowed()` (LoRa `{SET}`), plus the boot repair.

**1. The command gate in `commandAction(char*, bool)`** (`src/command_functions.cpp:822`), directly before `toggleApply()` (`:879`). That function is the choke point for the console, the TCP console 2323, web `manualcommand`, the web setup parameters, BLE text, RM1, T-Deck typed text and every `commandAction()` call in the code. The outer wrapper `commandAction(char*, int, bool)` (`:670`) splits chained lines (`--a --b`) and calls the inner function per sub-command; the gate has to sit in the inner function or a sub-command slips through.

- `prodLockRefuses(const char *cmd, bool instrument)` matches the first token after `--` exactly (the rule of `commandMatches`) against `nbrrelay`, `nbrsym`, `nbrreport`, `shortpath`, `pingtime`, `pingmax`, `specstart`, `specend`, `specstep`, `specsamples`. Additionally: `autoupdate auto` in all builds, `stor on` in production. It returns the name for the message, or `nullptr`.
- On a hit: print `[ERR];locked;<name>` (serial; for BLE also as a reply line via `addBLECommandBack()`), change nothing, `return`. The call reads `prodLockRefuses(msg_text+2, INSTRUMENT_ENABLED != 0)` and sits before `toggleApply()`.
- The value clamps for `--postime`, `--ptime`, `--maxhop` and `--txpower` stay in their parsers but call the same clamp functions (`prodClampPostime()`, `prodClampPtime()`) that the normalisation uses. One source for the bounds.

**2. The normalisation `prodLockNormalise(S &s, bool instrument, bool hasAutoUpdate)`** in `src/prod_lock.h` (a template over the struct type so the host test runs it against a stand-in; `hasAutoUpdate` is `false` on nRF52). It is idempotent and returns the number of changed fields. In all builds: `node_autoupd` 2 becomes 1, `node_postime` 1..299 becomes 300 and above 86400 becomes 86400, `node_parm_time` goes into 5..120 (0 becomes 15), `node_pingmax` above 5 becomes 5, `node_pingtime` outside 0 / 30..300 becomes 60. Production only, additionally:

- clears exactly the bits 0x3B00 (0x0100, 0x0200, 0x0800, 0x1000, 0x2000) in `node_sset4` and exactly bit 0x0400 in `node_sset`; `0x0400` in `node_sset4` (`--nbrdebug`) is left alone;
- leaves `node_pingmax` 0 or 1..5 alone (0 and 5 are equivalent) and sets `node_pingtime` to `node_pingcall[0] ? PING_INTERVAL : 0`;
- sets the four spectrum fields to 432.0 / 434.0 / 0.025 / 2048;
- sets `max_hop_pos` to `MAX_HOP_POS_DEFAULT`;
- sets `node_stor` to 0. `max_hop_text` (1..6) stays with the existing rule `maxHopTextSanitize()`.

Call sites of the normalisation (every path that writes past `commandAction()`):

Rejected alternatives:

- Normalising inside `save_settings()`: during load `save_settings()` on a half-loaded struct is dangerous (`src/esp32/esp32_flash.cpp:546-573` describes exactly that damage). The `pingtime` = f(`pingcall`) coupling would overwrite valid values.
- A `#if` in each setter: ten places a future command can forget. The gate with a name list plus the source scan in the test plan closes that.
- Compiling the four `--spec*` commands out in production: possible, but it does not cover blob, import and boot; the normalisation needs the fixed value anyway.

Boot behaviour: in production it writes only when something deviates (one flash write, idempotent afterwards). On already broken nodes the repair happens on the first boot of the new image. After that the runtime state (`bNBRRELAY` etc.) is consistent with the bits, because the flags are derived from the bits after the load.

Additionally on the web: the spectrum page no longer writes into `meshcom_settings` but works with local variables (see bug list); otherwise at 868 MHz it broke the fixed value with `863/870/0.100`.

## Bugs found while auditing

State of the implementation: bug 1 is fixed in range (text hop 1..6, position only in INSTRUMENT), the password question is decided (no password, approved security exception). Bugs 2 to 7 and 10 are fixed, 8 and 9 are covered by `prodLockNormalise()` and the range adjustment.

1. **`{SET}` has no password and too wide a range** (`src/loop_functions.cpp:2516-2550`). The branch sits in `sendDisplayText()` next to `{MCP}`; only `{MCP}` checks `cpasswd` (`:2443-2470`), `{SET}` checks nothing. It runs for frames not addressed to the node itself (`src/lora_functions.cpp:2083-2090`) and is not excluded from relaying (unlike `{ping}`/`{pong}`, `bMeshDestination` stays unchanged, `:2083-2090`). Effect: a single broadcast `{SET}n;m;` sets the persistent `max_hop_text` to 0..7 (outside 1..6, see `src/maxhop.h:17-18`) and the position hop limit to 0..7 (until reboot) on every node in radio range and on the relays behind them. With 0 no message leaves the node, with 7 it floods. Fix: accept text hop 1..6 only and ignore the position field in production; the password question (any sender vs gateway/operator only) is decided: no password, see questions.
2. **`--ptime` fallback is wrong** (`src/command_functions.cpp:6702-6713`, runtime side `src/esp32/esp32_main.cpp:4724-4727`, `src/nrf52/nrf52_main.cpp:2237-2241`). The range is 5..120 minutes, the fallback `TELEMETRY_INTERVAL` is `30 * 60` (`configuration_global.h:279`, a seconds value with a comment saying "minutes"). The timer then multiplies `* 1000 * 60` (`esp32_main.cpp:4730`): 1800 minutes = 30 hours. A typo such as `--ptime 200` stores 1800 and effectively switches telemetry off; the stored 1800 is itself outside 5..120 and is mapped to 1800 minutes again on every boot. The config import even allows 1800 explicitly (`config_json.h:323`: 0..1800). Fix: clamp to the nearest bound (or 15, the real default in `meshcom_settings.h:139`), fallback constant in minutes.
3. **`--postime`: dead branch and wrong way back** (`src/command_functions.cpp:1119-1139`). After the lower bound 300, `node_postime > 0` is always true; the `else` branch `posinfo_interval = POSINFO_INTERVAL` (`:1134-1135`) is unreachable. Consequence: `--postime 0` gives 300 s instead of the default 1800 s, and `--postime abc` (the `sscanf` failure leaves the old value 0 in place) sets 300 s, six times the position airtime. The comment says "minimum 3 Minuten", the code 5. Fix: 0 means default (the branch gets a purpose again), unparsable input is rejected.
4. **Several setters without parse check**: `--postime`, `--ptime`, `--pingtime`, `--pingmax` use a bare `sscanf` (`:1121`, `:6704`, `:3762`, `:3811`). A non-number stays as 0 or as the old value and is then clamped or set to the fallback. The other setters reject non-numbers (`cmdArgNotNumber`, `:736-749`).
5. **`--pingtime` accepts values the main loop ignores**: setter lower bound 15 (`:3764`), but the loops only send at `node_pingtime > 29` (`src/esp32/esp32_main.cpp:5109`, `src/nrf52/nrf52_main.cpp:2681`). 15..29 is stored but never pinged, yet still silences HEY and the neighbour report (`loop_functions.cpp:5436`, `5528`).
6. **`--pingmax max` contradicts `PING_MAX`**: it sets 100 (`:3800-3806`), the upper bound is 5 (`:3813`), the import allows 0..100. Also `--pingmax 7` resets to 5 instead of clamping.
7. **Spectrum settings are ineffective and overwritten**: `--spectrum` uses fixed values (`src/spectral_scan.cpp:138-166`); the web page sets `node_spec*` to 432/434/0.025/2048 on every request, or to 863/870/0.100 above 860 MHz (`web_functions.cpp:3927-3938`), and persists them with the next `save_settings()`. The command ranges (430..439 and 869.4..869.65, `command_functions.cpp:5463-5500`) do not match the page's values. `--specsamples` reports the unit "MHz" (`:5544`).
8. **nRF52 BLE blob without any check** (`src/nrf52/ble_settings_v1.cpp:229-420`, applied in `src/nrf52/nrf52_ble.cpp:514-552`): every field, including `node_sset`, `node_sset4`, `node_power`, `max_hop_text`, `max_hop_pos`, the ping and spectrum fields, is taken and saved. Boot later only checks radio parameters and `max_hop_text`.
9. **Config import has wide ranges** (`src/config_json.h`): postime 0..86400, ptime 0..1800, pingtime 0..86400, pingmax 0..100, spectrum 0..1e9. Implementation: `node_autoupd` 0..2 (2 is normalised to 1) and the spectrum fields in the setter ranges (start/end 400..960, step 0.01..2.0, samples 500..2048); ptime, pingtime and pingmax deliberately keep the old wide ranges so a backup from an earlier build stays importable, `prodLockNormalise()` repairs the values before saving.
10. **Cosmetic**: the help texts gave no ranges for `--postime 99` / `--ptime 99`. Fixed: `--postime 300..86400` and `--ptime 5..120` are in `--help` (`help_parity_lint` stays green).
