# Finder G — Paths from Topology/Horizon (4.3 ME-step, 4.4 Pfad/Horizont, Fehlerszenarien, Rollout Schritt 3)

## Candidates

### G1 — Horizon entries can be seeded from server-injected POS/HEY, contradicting the paper's own stated mitigation (HIGH)

Section: 4.4 "Pfad aus der Topologie und Horizont", rule "Horizont-Einträge entstehen aus Position und HEY mit mindestens drei Pfad-Token, nicht aus Text, aus demselben Grund wie im Kantenpool-Papier: vom Server eingespeister Text trägt Pfadpaare, die nie auf Funk gehört wurden."

Problem: the paper excludes only `Text` (`:`) as the server-injection vector and treats `!`/`@` as safe for building horizon entries. But `src/nbr_matrix.h` (lines 219-240, the header comment `nbrNoteFrame()` already documents against) states the underlying assumption explicitly and flags it as unresolved:

> "Restrisiko: das setzt voraus, dass der Server ausschliesslich Text nach unten schickt — udp_frame_esp32.cpp nimmt weiterhin '!'/'@' von UDP an."

I.e. the firmware's own UDP ingest path still accepts server-originated Position and HEY frames, not just Text. If a server-injected `!`/`@` frame is relayed onto LoRa by a gateway with a synthetic `<Server-Pfad>,<Gateway>` tail (same mechanism the paper itself describes for Text), the resulting frame is exactly the type (`!`/`@`, >=3 tokens) that 4.4's rule uses to _create_ horizon entries — including hop count and entry-row mask. This defeats the entire premise of 4.4 ("Absender ab 3 Hops bekommen einen Horizont-Eintrag ... über die sie hereinkommen" — over which rows they were actually heard on air): the hop-count and entry-row semantics silently become fictitious for any server-fed POS/HEY, not just Text.

Failure scenario: A gateway with Mesh on relays a server-side APRS position update (never heard on RF) with a synthetic path. The topology records a horizon entry with an entry-row and hop-count that never corresponded to an actual RF path. Anyone reading "DL8HW-12, 4 Hops, Eintritt DB0HOB-12" (as in Abb. 4) has no way to tell this apart from a genuine over-the-air observation.

Severity: HIGH — undermines the stated raison d'être of the horizon feature (reconstructing real RF paths) for exactly the frame types (`!`/`@`) the paper trusts, and the paper's own justification text explicitly claims parity with the (flawed, admittedly-Text-only) Kantenpool-Papier mitigation without acknowledging the residual-risk note already on file in the code it cites.

### G2 — 4.3's "relax token validation to last hop only" is not what the code currently does, and it directly contradicts the paper's own Fehlerszenarien row (HIGH)

Section: 4.3 "MHeard aus der Topologie", rule "Der ME-Schritt prüft nur das Token des letzten Hops. Ein Rahmen mit ungültigem Token weiter vorn oder mit Schleife verliert wie heute seine Kanten, zählt aber als Direktempfang, weil MHeard ihn heute auch zählt." vs. section 5 Fehlerszenarien row "Rufzeichen außerhalb der Zeichenregel | Erkennung: DROP TOK im Schattenlog | Reaktion: keine Zeile | Lücke: **Station fehlt in MHeard, die heute dort stünde**; ... | ab Stufe 1".

Problem: today `nbrNoteFrame()` validates the _whole_ path before touching anything (`src/nbr_matrix.h:212-217`, corroborated by the function comment at 249-259): "verletzt das ein Token oder gibt es mehr als 8, wird der GANZE Frame verworfen (-1, Log: DROP TOK)... Kommt ein Rufzeichen zweimal vor (Schleife), wird ebenso verworfen (-2, DROP LOOP)." Both checks "laufen über den GANZEN Pfad" and abort the frame unconditionally — the ME hit (`cell[letzter_hop][0]`, the thing 4.3 wants to reuse as the MHeard key) is never reached in either case. That's a real behavioral change 4.3 needs, not something that "läuft heute schon" as the section's lead sentence claims.

`updateMheard()` (src/mheard_functions.cpp:299 ff.) confirms the asymmetry: it never inspects the path at all, only `mh_callsign` (the last hop), so today's real MHeard _does_ register a station whose upstream path has a malformed token or a loop — exactly the parity 4.3 wants for the ME step. So the target behavior 4.3 describes is achievable, but it requires **decoupling the ME hit from the whole-path DROP TOK/DROP LOOP check** in `nbrNoteFrame()` — a genuine code change that belongs in the Rollout/Umbaustellen inventory, not an already-existing behavior.

More importantly, the paper's own Fehlerszenarien table (section 5) directly contradicts 4.3's carve-out: it lists "Rufzeichen außerhalb der Zeichenregel" (DROP TOK) as producing "keine Zeile" and "Station fehlt in MHeard, die heute dort stünde" — with no stage-dependent caveat, "ab Stufe 1" onward, i.e. it still applies after the switchover (Stufe 3) where nbr_views is the _only_ MHeard source. If 4.3's relaxation had actually shipped, this scenario row should say "ME still counts, only the window rows/edges are lost" (the way 4.3 promises) — not "station missing from MHeard". The two sections cannot both be right as written.

Also unaddressed: the DROP LOOP case ("...oder mit Schleife...") is mentioned in 4.3's prose but has **no row at all** in the Fehlerszenarien table, and no test/acceptance criterion in the Rollout table (step 2's `native_nbr_views` test only promises "MH-JSON... feldgleich... bis auf... B2", nothing about DROP TOK/LOOP parity).

Severity: HIGH — an unflagged internal contradiction between the design section and the risk register for exactly the mechanism (MHeard-from-topology) this paper is supposed to be validating; it also means the Umbaustellen/Rollout inventories are missing a concrete code change (decoupling ME from full-path validation) that 4.3 depends on.

### G3 — Stale minimum-hop-count on partial horizon-entry eviction (MEDIUM)

Section: 4.4, rule "Die Hop-Zahl ist die kleinste im Fenster gesehene, last_min die letzte" + "Verdrängt wird der am längsten nicht gesehene Eintrag. Wird eine Zeile verdrängt, löscht der Durchlauf ihr Bit auch in allen Eintrittsmasken; ein Eintrag mit leerer Maske wird frei."

Problem: the hop-count stored per horizon entry is a single scalar minimum ever observed within the 12h window, decoupled from _which_ entry-row produced it. The eviction rule only says a row's bit is cleared from the entry mask when that row is evicted (and the whole horizon entry frees only when the mask becomes empty) — it says nothing about recomputing the minimum hop-count when the specific entry-row that produced that minimum is the one evicted while other (longer) entry-rows remain. Example: DL8HW-12 first seen via a 3-hop path (entry row A, hop=3); later also seen via a 5-hop path through a different entry row B (hop stays 3, min unchanged, but B's bit is now also in the mask); row A ages out and gets evicted (>12h idle even though the horizon entry itself is still fresh via B). The horizon entry survives (mask still has B's bit) but keeps reporting "3 Hops" even though the only reachable entry (B) is actually 5 hops — the displayed hop-count and the actually-reachable path are now inconsistent, with no rule to detect or correct it.

Severity: MEDIUM — display/diagnostic inaccuracy (the number shown for a far sender's distance can outlive the path it was measured on), not a memory-safety or decision-path bug, but it directly affects the one new number (hop count) the whole horizon feature is built to expose.

### G4 — No reconciliation between a horizon entry and a same-callsign row when a far source becomes a real 2-hop/direct row (MEDIUM)

Section: 4.4 (implicit gap; also relevant to Fehlerszenarien, which has no row for this case).

Problem: `hzCall[]`/horizon entries and `nbrCall[]`/matrix rows are separate arrays (per the component table in section 3: `nbrCall[R]` vs. `hzCall[H], hzEntry[H], hzMeta[H]`). If a station currently tracked only as a horizon entry (heard 3+ hops away) is later heard via a shorter path that falls inside the 2-hop window, it gets a _new, independent_ row (per 4.4's own path-construction rule: "Ein Weg für eine 2-Hop-Zeile X ist X, dann ein direkter Nachbar B..."). Nothing in the paper (rules under 4.4, nor Fehlerszenarien) describes removing, merging, or otherwise invalidating the now-stale horizon entry for the same callsign. Until the horizon entry separately ages out (its own last_min-driven eviction), the same station would be representable twice — once as a real, short row with concrete edges, once as a horizon entry with a possibly contradictory (and, per G3, possibly stale) hop count and entry-row. A UI/nbr_views reader (e.g. the Pfad page or App) would need an explicit tie-break rule that the paper does not specify.

Severity: MEDIUM — a plausible field occurrence (path lengths to marginal/far stations fluctuate with propagation) with no specified resolution, risking inconsistent duplicate display.

## Confirmed-fine checks

- **Edge direction convention**: `cell[X][Y] = "Y hat X gehört"` (src/nbr_matrix.h:160) is used correctly and consistently throughout the paper's `heardBy(X)`/`hears(x)` terminology (3. Zielbild component table; 4.4's path construction; 4.5's `HM = rows[ich].heardBy`; 4.8's `hears(m)`). Cross-checked against `nbrHearers()`/`nbrHearersMask()` doc comments (nbr_matrix.h:404-408, 458-461) — direction matches.
- **Figure 4 fixture numbers verified exactly against Anhang B** (`~/Desktop/Nachbarschaftsmatrix-Kantenpool.html`, raw edge list `X,Y,Summe`): edges `2,1,610` (DL2JA-2→DK5EN-98), `5,1,750` (DB0ED-99→DK5EN-98), `6,5,358` (DB0HOB-12→DB0ED-99), `6,2,53` (DB0HOB-12→DL2JA-2) map onto the four arrows and labels (358/53/750/610) in the MeshCom5-Topologie-als-Quelle.html SVG (lines 548-558) in the correct direction and value. No discrepancy found.
- **"Eintrittszeile ist das vorletzte Token" (entry row = second-to-last token)** is correct: verified against the 2-hop window rule `start = (ntok>2) ? ntok-2 : 0` (nbr_matrix.h:242-247) and against the live/Abb.4 example (`DL8HW-12,DL2RN-13,DB0HOB-12,DB0ED-99`, ntok=4 → start=2 → window = {DB0HOB-12, DB0ED-99} → entry = p[ntok-2] = DB0HOB-12, matching "Eintritt DB0HOB-12" in the figure). DL2RN-13 (the name the old path table keeps but the topology "intentionally doesn't know") sits at p[1], outside the window — this is the figure's whole point, not an inconsistency.
- **Hop-count semantics**: `msg_last_path_cnt` (aprs_functions.cpp:202,232) starts at 1 and increments per comma in the source path, i.e. it equals the token count (sender + relays), which equals the number of RF hops to the receiving node (each token boundary is one transmission, plus the final hop into the receiver). DL8HW-12's "4 Hops" for a 4-token path (`DL8HW-12,DL2RN-13,DB0HOB-12,DB0ED-99`) checks out, and matches the on-air display format `%01u%s` at web_functions.cpp:1559 (`mheardPathLen & 0x7F` + G-flag).
- **"Path table keeps the shortest path within 12h"**: confirmed against `mheard_functions.cpp:622`, `if((mheardPathLen[ipos] & 0x7F) < mheardLine.mh_path_len) return;` — replacement is skipped only when the _existing_ entry is strictly shorter than the incoming one; ties and shorter-or-equal always replace. Combined with the unconditional 12h prune sweep at the top of `updateHeyPath()` (mheard_functions.cpp:577-603, `mheardPathFreshMs`), the "shortest path within the last 12h, last-writer-wins on ties" characterization is accurate.
- **Horizon entries excluded for Text** (4.4's rule, and 4.3's "Text feeds only ME") is correctly derived from and consistent with the `nbrNoteFrame()` doc comment (nbr_matrix.h:219-240), including the reasoning about server-injected Text via gateway relay.
- **DROP FULL practically unreachable at the target row counts**: confirmed via nbr_matrix.h:257-259 ("bei NBR_MAX_ROWS >= 3 ... praktisch nie mehr erreichbar") — with target NBR_MAX_ROWS of 64/128 (section 4.2) this is correctly negligible, so the paper's implicit "always has a row after commit" claim holds modulo this already-documented, now even-more-negligible edge case.
- **Sizing math for 40/96 horizon slots vs. ~30/76 today**: arithmetic checks out (0.76 × 40 ≈ 30 classic; 0.76 × 100 = 76 S3/nRF52), and matches the _now_ re-measured "22/29" figure directionally (majority of path entries are far senders), though see note below on stability of that ratio.

## Supporting live-data note (not a paper defect, but a caveat on the sizing premise)

Live re-check via `curl http://dk5en-98.local/?page=path` at 2026-09-24 ~21:42 (paper's snapshot was 06:29–08:55 the same day) returned exactly 29 path entries (matches the paper's count), but with hop distribution `{2:11, 3:11, 4:5, 5:2}` → 18/29 (62%) far senders, vs. the paper's cited 22/29 (76%) some 13 hours earlier. The paper already labels this a "Momentaufnahme" (snapshot) and states the caveat explicitly in section 2 ("Mengengerüst"), so this is not an undisclosed flaw — but it is worth noting for reviewers that the ratio driving the 40/96-slot sizing decision moved by 14 points within the same day on the same node, which is a thinner empirical base than the single fixed "76%" figure used throughout section 4.4's premise paragraph might suggest.
