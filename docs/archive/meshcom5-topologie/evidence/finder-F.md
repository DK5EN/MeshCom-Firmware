# Finder F — Phone App / BLE / MH JSON / MHeard displays

## Candidates

### F1. DIST worst-case length is computed with Python's float formatting, not ArduinoJson's — the real worst case is ~2x longer than assumed, and eats most of the claimed 20-byte safety margin

- **Section**: 4.6 (Mengengerüst row "MH-Rahmen an die App, schlimmster Fall: 162 B / 225 B, Grenze 245 B")
- **Problem**: `~/Desktop/MeshCom5-Topologie-als-Quelle.build.py` computes `J_BASE`/`J_NEW`/`J_POS` with Python's `json.dumps({"DIST": 1234.5, ...})`. Python prints `1234.5` (6 chars). But the firmware value is `mheardLine.mh_dist`, a **`double`** (`src/aprs_structures.h:148`), written **unrounded** straight into the JsonDocument (`src/mheard_functions.cpp:430`, `:916`; comment at `src/mheard_record.h:65-70` explicitly says the live path "gibt mh_dist UNGERUNDET ins JSON"), and it comes from `gps.distanceBetween(...)/1000.0` (`src/lora_functions.cpp:1166`) — an arbitrary irrational-looking double, never a clean literal like `1234.5`.
  ArduinoJson v7's `TextFormatter::writeFloat<T>(T value)` (`.pio/libdeps/native/ArduinoJson/src/ArduinoJson/Json/TextFormatter.hpp:68-70`) calls `writeFloat(JsonFloat(value), sizeof(T) >= 8 ? 9 : 6)` — for a `double` (8 bytes) it asks for up to **9 fractional digits**, not a shortest-round-trip or fixed-1-decimal representation. `decomposeFloat()` (`Numbers/FloatParts.hpp`) reduces the digit budget by the number of integral digits and strips trailing zeros, but for a non-round distance value the realistic worst case is an integral part (1-4 digits) plus 5-9 significant fractional digits, e.g. `"1234.567891"` — **11 characters**, not the assumed `"1234.5"` (6 characters). That is a **+5 byte** underestimate on DIST alone, in both the base-13-field frame and the +7-field frame (the DIST field is reused unchanged in both).
- **Compounding underestimates found in the same worst-case model**:
  - `mh_snr` is `int8_t` (range -128..127); the generator's `base` dict uses `"SNR": -20` (3 chars) but the true worst case is `"-128"` (4 chars, +1 byte). The new `HM` field (also an SNR-typed int8) has the same issue.
  - `mh_path_len`/`PL` is `uint8_t` (0-255); generator uses `"PL": 15` (2 chars) vs. true worst case `255` (3 chars, +1 byte).
  - `CALL` (see F2 below) can be far longer than the assumed `"OE7XWT-12"` (9 chars).
- **Failure scenario**: Combine the corrected DIST (+5), SNR (+1), PL (+1) and a realistic-but-not-pathological CALL (+3-5, see F2) and the paper's claimed 225 B worst case for the 20-field frame becomes **~235-245 B** — right up against, or over, the 245-byte ceiling the paper itself treats as the hard wall. The 20-byte margin the paper relies on ("225 B, Grenze 245 B") is not a real 20-byte margin once ArduinoJson's actual double formatting is used instead of Python's.
- **Severity**: High — this is the load-bearing number for the entire "7 new fields fit" decision in 4.6, and it is computed with the wrong serializer's semantics.
- **Evidence**: `~/Desktop/MeshCom5-Topologie-als-Quelle.build.py:70-76` (J_BASE/J_NEW via `json.dumps`); `.pio/libdeps/native/ArduinoJson/src/ArduinoJson/Json/TextFormatter.hpp:68-70` (`writeFloat` decimal-place selection); `.../Numbers/FloatParts.hpp` (`decomposeFloat`); `src/aprs_structures.h:148` (`double mh_dist`); `src/mheard_functions.cpp:430,916`; `src/mheard_record.h:60-70`; `src/lora_functions.cpp:1166`.

### F2. CALL worst-case length assumed as 9 chars ("OE7XWT-12"); the buffer and the parser allow up to 20

- **Section**: 4.6, Mengengerüst
- **Problem**: `mh_callsign` is `char[MC_CALL_LEN_Z]` with `MC_CALL_LEN_Z = 21` (`src/aprs_structures.h:55,138`), i.e. up to 20 usable characters. It is filled via `mcSet(mheardLine.mh_callsign, sizeof(...), aprsmsg.msg_source_last)` (`src/lora_functions.cpp:1078`) — a bounded copy of whatever token the APRS/TNC2 parser extracted as the "last hop" callsign, with no amateur-radio-format check (6 chars + `-SSID`) enforced at that point. A well-formed callsign is indeed short (matches the paper's 9-char assumption), but the storage and the copy path do not themselves guarantee that; a malformed or unusual path token can legitimately reach up to 20 characters before being clamped by `mcSet`.
- **Failure scenario**: An oddly-formed digipeater/path token (or, more mundanely, any future relaxation of path-token validation) produces a CALL value near the buffer limit, adding up to +11 bytes versus the paper's assumed 9-char worst case — on top of F1's DIST/SNR/PL underestimates, this can push the 20-field frame over 245 B.
- **Severity**: Medium (lower confidence than F1 — depends on how strict upstream path-token validation actually is, which this review did not fully trace).
- **Evidence**: `src/aprs_structures.h:55,138`; `src/lora_functions.cpp:1078`.

### F3. Paper says "245 Byte" is _the_ command-frame limit; the two call sites actually enforce two different limits, and only the tighter one truncates the raw byte stream

- **Section**: 4.6 ("Prämisse für die Länge: Ein Kommando-Rahmen darf 245 Byte lang sein")
- **Problem**: There are two different outgoing paths and two different limits:
  - Live push (`updateMheard()` → `addBLEOutBuffer()`, `src/mheard_functions.cpp:436-440`): `addBLEOutBuffer()` (`src/loop_functions.cpp:669-676`) clamps JSON ('D') frames to `UDP_TX_BUF_SIZE` = **255** (`src/configuration_global.h:266`), not 245.
  - List-on-connect (`sendMheard()` → `addBLEComToOutBuffer()`, `src/mheard_functions.cpp:923-929`): `addBLEComToOutBuffer()` (`src/loop_functions.cpp:709-719`) hard-clamps to **245** and, critically, does so by **truncating the already-serialized byte buffer** (`len = 245;` then `bf_push(&phoneComRing, buffer, (uint8_t)len)`), not by re-serializing a smaller document. If `frame_len` (built by plain `bleJsonFrame()`, not the fail-soft variant, in both current call sites) ever exceeds 245, the bytes handed to the ring are a JSON object cut off mid-content — not a valid JSON document.
  - The phone app treats this as fatal, not degraded: `MessageHandler.ts` (case `0x44`/`"{"`, ~line 793-799) explicitly checks `if (!json_str.endsWith("}"))` and **drops the entire frame** with only a console error if it doesn't. There is no partial-parse fallback.
- **Failure scenario**: If the 20-field worst case (see F1/F2) exceeds 245 B and `sendMheard()` is not switched to `bleJsonFrameFailSoft()` (the paper's text only says "Der Rahmen wird mit bleJsonFrameFailSoft() gebaut" in the singular, without naming which of the two call sites, or with what `payload_max`), the **list-on-connect path silently loses entries** — a truncated MH JSON is pushed into `phoneComRing`, fails the app's `endsWith("}")` check, and is discarded. The live-push path has 10 more bytes of headroom (255 vs. 245) and would tolerate a somewhat larger frame before hitting the same failure mode.
- **Severity**: High — this is a real functional risk if the length premise in F1 is even approximately right, and the paper's single "245" number obscures that the two paths need separate, correctly-chosen `payload_max` values passed to `bleJsonFrameFailSoft()` at _both_ call sites, not just a stated intention.
- **Evidence**: `src/loop_functions.cpp:669-676` (`addBLEOutBuffer`, UDP_TX_BUF_SIZE=255 cap for 'D'); `src/loop_functions.cpp:709-719` (`addBLEComToOutBuffer`, hard 245 clamp on already-serialized bytes); `src/configuration_global.h:266`; `src/mheard_functions.cpp:436-440,923-929` (both current call sites use `bleJsonFrame()`, not the fail-soft variant); `~/WebDev/Meshcom-MobileApp/src/hooks/MessageHandler.ts:793-799` (`endsWith("}")` guard, frame dropped on failure).

### F4. `bleJsonFrameFailSoft()` correctly drops the last-inserted (trailing) member each pass — confirmed fine, but the guarantee is order-dependent and unstated as a contract

- **Section**: 4.6 ("...streicht zuerst die hintersten Felder, also die neuen, nie die alten")
- **Check**: Read `src/ble_json_frame.h:42-60`. The `while` loop iterates all `JsonPair`s in the object on every pass and keeps overwriting `drop` with the last non-"TYP" key seen; since ArduinoJson's `JsonObject` iterates in insertion order, this reliably removes the **most-recently-inserted** member first, one per pass, until the document fits or only `TYP` remains. The paper's claim is correct **provided the implementation appends the 7 new fields (AGE, HM, ROLE, EX, NB, GW, VIA) strictly after all 13 old fields** in the `JsonDocument` insertion order — which is an implementation discipline, not something the function itself enforces or documents as a precondition. A future edit that inserts a new field in the middle (e.g. adding `ALT` between `DIST` and `PL` for a later web-only extension of the same doc) would silently invert the drop priority for everything inserted after it.
- **Severity**: Low/Note — mechanism is sound and matches the described behavior, but the "never drops old fields" guarantee rests entirely on call-site insertion order discipline, with no assertion or test enforcing it.
- **Evidence**: `src/ble_json_frame.h:42-60`.

### F5. Section 4.3's claim "ohne gültige Uhr ... geht wie heute kein MH-Rahmen" (today, without a valid clock, no MH frame goes to the app) does not match the current code — there is no clock-validity gate on the MH send path

- **Section**: 4.3 (line: "Ohne gültige Uhr arbeitet die Topologie weiter, ... und an die App geht wie heute kein MH-Rahmen."), with direct consequences for 4.6 since the app timestamps and dedups MH entries by DATE/TIME (see F6).
- **Problem**: Searched the live-path code that builds `mheardLine.mh_date`/`mh_time` (`src/lora_functions.cpp:1088-1093`) and the send path (`src/mheard_functions.cpp:405-440`): there is no check of clock validity anywhere in this call chain before `addBLEOutBuffer()` is invoked. `mcSet(mheardLine.mh_date, ..., getDateString().c_str())` / `getTimeString()` are called unconditionally, and whatever those return (including any default/epoch string when the RTC is unset) is what ships to the phone. The only other consumer that treats an early/invalid date specially is `updateHeyPath()`, which skips inserting path/horizon rows for dates before 2025 (`src/mheard_functions.cpp:482-483`) — that check exists for the (still-current 4.4-era) Pfadtabelle path, not for the MH-to-phone path.
- **Failure scenario**: If the paper's Stufe-3 "no clock → no MH frame" behavior is actually a **new** restriction (not, as claimed, a continuation of today's behavior), that's a legitimate design decision but the paper misrepresents it as "wie heute", which understates the behavior change for anyone diffing old vs. new app-visible behavior on nodes that never get a GPS/NTP fix (e.g. indoor gateways).
- **Severity**: Medium — factual/premise error, not by itself a crash, but it means the campaign's own "unchanged from today" framing is wrong for this specific path, which matters given the paper's stated commitment to a `[TOPO]|DIFF` shadow-log parity check against `updateMheard()`.
- **Evidence**: `src/lora_functions.cpp:1088-1093`; `src/mheard_functions.cpp:405-440` (no clock check in the JSON-build/send path); `src/mheard_functions.cpp:482-483` (clock check exists only for Pfad/Horizont, not MH).

### F6. Confirmed fine: app tolerates unknown/extra JSON fields, and dedups MH entries by callsign showing only the latest — but the effective "checkJSON" validation the paper implicitly relies on is a no-op

- **Section**: 4.6 ("Die alte App liest nur ihr Interface und ignoriert die neuen Felder" / "Die App zeigt ohnehin nur den letzten Stand je Rufzeichen")
- **Check**: `MessageHandler.ts` case `"MH"` (~1188-1260) does `const mheard: Mheard = json_data` — a TypeScript cast with **no runtime schema validation** — and only reads the 13 known keys (`CALL, DATE, TIME, RSSI, SNR, HW, DIST, PL, MESH, NCNT`); the 7 new fields are never referenced anywhere in the app source (`grep` for `AGE`, `ROLE`, `\bEX\b`, `\bNB\b`, `\bGW\b`, `\bVIA\b` in `MessageHandler.ts`/`AppInterfaces.ts` found nothing beyond the paper's own field list). This confirms "old app ignores new fields" as **true**.
  `MheardStaticStore.setMhArr()` (`src/utils/MheardStaticStore.ts:19-70`) dedups incoming MH records by `mh_callSign + mh_nodecall`, replacing the stored entry and re-sorting by `mh_timestamp` descending — confirming "shows only the latest per callsign" as **true**, and the UI (`pages/Mheard.tsx`) renders straight from that deduped, single-entry-per-station store.
  Side note (not paper-relevant, but adjacent risk): `checkJSON()` (`MessageHandler.ts:1334-1346`) is a documented-looking guard against `undefined`/`null` fields, but its `keys.forEach(...)` callback `return false` only exits the forEach callback, never the outer function — `checkJSON()` **always returns `true`**. This means a partially-missing/undefined field (e.g. from a bug in a future fail-soft drop that accidentally includes `DIST` in the droppable set) would NOT be caught here and would only surface as a runtime crash at first use (e.g. `mheard.DIST.toFixed(2)` on `undefined`, `MessageHandler.ts:1254`). This is a pre-existing app bug, independent of the paper, but it means the paper's implicit assumption that "extra/missing fields fail safe" in the app is only true for _extra_ fields, not for a field the app expects that ends up missing.
- **Severity**: Low (documents two of the paper's claims as verified correct) / Medium note on `checkJSON()` and the `mheard.DIST.toFixed()` crash risk if DIST were ever dropped.
- **Evidence**: `~/WebDev/Meshcom-MobileApp/src/hooks/MessageHandler.ts:1188-1260,1334-1346`; `~/WebDev/Meshcom-MobileApp/src/utils/MheardStaticStore.ts:19-70`; `~/WebDev/Meshcom-MobileApp/src/pages/Mheard.tsx`.

### F7. Live-push throttle (once per neighbour per minute) matches the app's own timestamp semantics — confirmed safe

- **Section**: 4.6 ("Live-Rahmen höchstens einmal je Nachbar und Minute")
- **Check**: `MheardStaticStore.setMhArr()` computes `mheard.mh_timestamp = new Date(mheard.mh_date + "T" + mheard.mh_time).getTime()` (`MheardStaticStore.ts:24-25`) — i.e. the app's own "last heard" timestamp is derived from the frame's DATE/TIME fields, not from BLE arrival time, and only whole-second resolution is available regardless of push frequency. A once-per-minute-per-neighbour throttle (keyed on `last_min` changing) cannot make this worse: today's every-frame push already only carries second-level granularity, and since entries are upserted by callsign (not appended), reducing push frequency just reduces redundant identical-timestamp updates, never loses information the app currently displays (age, RSSI/SNR snapshot, NCNT). No consumer in the app computes packet rate, inter-arrival time, or any statistic from _how often_ MH frames arrive — confirmed by grep across `MessageHandler.ts`/`MheardStaticStore.ts`/`Mheard.tsx`/`Map.tsx` for anything keyed off push frequency.
- **Severity**: N/A (confirmed fine).
- **Evidence**: `~/WebDev/Meshcom-MobileApp/src/utils/MheardStaticStore.ts:19-70`; `~/WebDev/Meshcom-MobileApp/src/hooks/MessageHandler.ts:1188-1260`.

Neither reads `mh_dist`, ALT, or any position field. This matches the paper's classification of ALT as web-only and DIST/PL/MESH as not used by the T-Deck table view.
- **Severity**: N/A (confirmed fine, one caveat below).

- **Evidence**: `src/mheard_functions.cpp:1103+`; `src/t-deck-pro/ui_deckpro.cpp:1275-1310`; `src/t-deck-pro/tdeck_pro.cpp:587-589`.
