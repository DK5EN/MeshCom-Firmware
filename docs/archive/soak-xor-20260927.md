# Soak protocol: PN-XOR retry, 2026-09-27

> **ARCHIVED 2026-10-07.** soak protocol for the 2026-09-27 XOR run, evaluated in `../soak-20260928-verdict.md`; PR #1168 merged. Body unchanged.

## Purpose

Run the PN-XOR direct-message retry firmware (branch `feature-snf`, PN-02 /
`dk5en-xor`) for 24 h between two of our own nodes and confirm it is stable
under real traffic before it goes further: no reboot, no heap drift, every
test DM acknowledged (or its failure explained), no NBR-matrix consistency
violation, and both capture pipelines staying alive for the whole window.

## Test traffic

`tools/bench/soak_dm.py` sends one DM every 15 minutes overall (30 minutes
per direction, the two directions offset by half an interval), alternating
`DK5EN-1 -> DK5EN-98` / `DK5EN-98 -> DK5EN-1`, text
`"soak 20260927 #<seq> <from>><to>"`. Only direct DMs between the two nodes,
never `*` or a group (operator rule: no broadcast test messages). Its own
log: `~/meshlog/soak-dm-20260927.log`, one line per send:
`<iso time>  SEND <seq> <from> <to> <http status> <node answer>`.

## Window

2026-09-27 17:39 -> 2026-09-28 17:39 (24 h).

## Acceptance criteria

1. No reboot on either node.
2. Last heap sample >= (first heap sample after `--since`) - 1024 B, per
   node.
3. Every test DM acked, or its non-ack explained (give-up, send failure,
   capture gap).
4. Zero NBR-matrix `CHECK` violations (extra/missing/bad/dup edges) on
   either node.
5. Both captures alive: no gap between two consecutive log lines longer
   than 10 minutes.

## Running the status report

```sh
python3 tools/soakstatus.py --self-test
python3 tools/soakstatus.py --fetch --since "2026-09-27 17:39" \
    --out docs/soak-status-latest.md --json docs/soak-status-latest.json
```

`--fetch` pulls DK5EN-98's day-stamped log file(s) (`YYYY-MM-DD.log`, one per
calendar day the window touches) plus `status.txt` from the rpizero logger
via `scp`; it never opens the node's own console (that connection is
single-client and belongs to the logger). Reboot detection, capture-gap
detection and NBR `CHECK` violations are computed by
`tools/nbrlog.py`, invoked as a subprocess against a time-sliced copy of
each node's log -- `tools/soakstatus.py` does not re-implement NBR parsing.
Everything else (heap, channel utilization, DM setlog counters, the
`[RETX]`/`[RX]` retry-ladder markers, and the per-test-DM correlation) is
`tools/soakstatus.py`'s own.

The firmware's `"[LOG] DM sent=..."` line resets every counter on print
(`dm_stats.cpp`'s `dmStatFormat()` reads each one via
`std::atomic::exchange(0)`), so each line is a delta since the previous
print (every 300 s under `--setlog on`), not a running total. The report
therefore sums all such lines across the window rather than showing only
the latest one.

## Known limits

Both nodes hear each other directly at roughly -75 dBm. At that link
quality the PN-XOR retry ladder mostly won't trigger -- a DM either gets
its ack on the first attempt or, on the rare loss, gets a fast direct
retry. This soak proves 24 h stability and the ack path (LoRa and
server/UDP), not multi-hop loss recovery or how well the retry logic
degrades under a marginal link; that's `BACKLOG` item PN-01, and needs a
node pair with a real multi-hop or fringe-signal path between them.

### Final evaluation (2026-09-29)

The run did not deliver the planned 24 h two-node window. Full verdict with
evidence: [`soak-20260928-verdict.md`](soak-20260928-verdict.md).

- The test-DM sender and DK5EN-1's capture were both killed host-side at
  2026-09-27 18:52 ("END sent=5"), so the two-node XOR data covers 73 min.
  `soakstatus.py` does not flag a capture that dies before `--until` (verdict
  Finding 8, T3).
- DK5EN-98 ran the full 26 h capture, but was OTA-flashed twice: 09:11 to
  v4.35u.09.28-neo and 14:26 to v4.35u.09.28.2-neo. The XOR build itself ran
  15.6 h on DK5EN-98 only.
- Criteria against DK5EN-98, per phase: no unplanned reboot (PASS), heap
  129204->130412 / 129580->128972 / 129744->129736 (PASS), 0 NBR CHECK
  violations in 1558 checks (PASS), no capture gap > 60 s (PASS). DMs: 5/5
  test DMs acked, 14/15 own DMs acked in P1 (the one give-up was a deliberate
  timeout test), 3/3 in P2, 15/15 inbound acked.
- The two PN-retry fixes in fed0eb0e (8b3d70ba, 949dba25) were never
  exercised: 0 own retry copies came back via the server, and no binary ACK
  referenced an own DM. Verifying them needs bench injection.
- DK5EN-1 had one unplanned TASK_WDT reset on the 17:14:17 build (verdict
  Finding 3).
