# Review: PR #1114 — KISS/TCP interface (ESP32)

**PR:** icssw-org/MeshCom-Firmware #1114, `raltenbrand:kiss-mode` → `dev`
**Head reviewed:** 627ff1e7 (v1.3), diff base upstream/dev 2cb6bb4d (= merge base, no rebase needed)
**Diff size:** +1937 / −10 across 16 files
**Date:** 2026-09-01
**Method:** rule-based code-quality audit (mechanical scan + contextual verification) followed by
an 8-angle independent review with mandatory adversarial verification of every load-bearing
finding. All 7 standard build environments compiled; RAM/Flash deltas measured against an
upstream/dev baseline built with the same toolchain.

---

## 1. Executive summary

This is a well-engineered PR. The architectural decision (tap at the deduplicated frame level
instead of a PHY bypass) is correct for this codebase, the implementation consistently reuses
proven in-tree patterns (`externQueue`, `net_console` socket handling), memory safety is solid —
every attacker-reachable `memcpy`/index in the new parser is properly bounded — and the
"disabled = unchanged" claim holds: the nRF52/RAK4631 build is byte-count-identical with zero
KISS symbols in the ELF, and an ESP32 build with `-D DISABLE_KISS_TCP` returns to baseline RAM.

The review still found real functional gaps that should be addressed before (or immediately
after) merge, none of which invalidates the design:

1. **The APRS ACK bridge is one-way** — a KISS client can _receive_ MeshCom DMs but its standard
   APRS ack never stops the sender's retransmissions; worse, it is re-injected as a junk text DM
   that the sender then acks back (traffic amplification). This undercuts the headline feature of
   v1.3.
2. **SSIDs 16–99 are silently collapsed to SSID 0** in the AX.25 encoder. MeshCom callsigns use
   two-digit SSIDs routinely, so distinct stations merge on the client's screen.
3. **`--kiss off` on a KISS-only node never closes port 8001** (the stop call sits inside a block
   that is no longer entered) — an unauthenticated port stays open, with the client attached,
   until reboot.
4. **A `{` anywhere in a message body truncates the message** (over-eager APRS message-number
   extraction).
5. **After a WiFi drop, a stale client socket can block the single client slot forever** (no
   liveness probe, no teardown on reconnect).

Plus a set of medium items (no TX rate limit driving a full NVS rewrite per injected frame, the
documented `::text` broadcast form injecting a stray colon, mid-frame truncation on TCP
backpressure producing corrupt frames instead of dropped ones, wrong destination field once
`--via` is in the path) and a process gap: **zero automated tests** for a parser fed by untrusted
TCP input, although the repo ships a native Unity harness (`env:native_extradio`) built for
exactly this shape of code.

**Recommendation: request changes, merge after a fix round.** Items 2–5 and the via-field bug
are one-to-five-line fixes. Item 1 (ack bridging) needs a small design decision (translate
client acks into `SendAckMessage()` format, or document DM ack semantics as out of scope for v1).

## 4. Verified findings

Every finding below survived adversarial verification (independent re-derivation against the
code); trigger conditions were corrected where the first analysis was wrong.

### High

**F1 — APRS ack translation is one-way: a KISS client cannot ack a MeshCom DM**
`src/kiss_functions.cpp:381-425` · verified end-to-end
The v1.3 ack map correctly rewrites _incoming_ acks for the client. The reverse direction does
not exist: a client's standard APRS ack (`:OE1ABC   :ack123`) is treated as an ordinary message,
`sendMessage()` strips the `{OE1ABC}` destination and — because it is a DM — appends its own ack
request, so the on-air payload becomes `ack123{NNN`. No MeshCom ack detector matches it (all
sites require `indexOf(":ack") > 0`: `lora_functions.cpp:870/873`, `udp_functions.cpp:255`), so
the original sender keeps retransmitting, displays the junk text "ack123", **and acks the junk
ack back** — net traffic amplification instead of an ack. The node's own auto-ack only fires for
an exact node-call match (`lora_functions.cpp:830`), i.e. never for the SSID-variant client call
the PR's callsign gate is designed to allow. Fix shape: detect `:ackNN`/`:rejNN` info fields in
`handleInboundAx25()` and route them through `SendAckMessage()`-equivalent formatting instead of
`sendMessage()` (or document DM acks as unsupported in v1 and drop them instead of injecting).

**F2 — SSIDs 16–99 silently collapse to SSID 0 in the AX.25 encoder**
`src/kiss_functions.cpp:171-172` · verified
`if (ssid < 0 || ssid > 15) ssid = 0;` — but MeshCom callsigns legitimately carry two-digit
SSIDs (`regex_functions.cpp:9` allows them; real meshes use -20…-99 routinely). Every such
station is emitted to the client as the **base call** (SSID 0), merging distinct stations into
one and misdirecting client replies. AX.25 has only 4 SSID bits, so a lossless mapping is
impossible — but clamping to 0 is the worst choice. Options: drop such frames, clamp to 15, or
document the aliasing. The reverse direction (client addressing -16…-99) is equally impossible
and worth a doc note.

**F3 — `--kiss off` never closes port 8001 on a KISS-only node**
`src/esp32/esp32_main.cpp:3730, 3809-3822` · verified by brace-level analysis
`kissStop()` sits inside `if(bWEBSERVER || bEXTUDP || bGATEWAY || bNETCONSOLE || bKISS)`.
On a node where the other four are off (the plain KISS-bridge deployment this PR enables),
`--kiss off` makes the outer condition false — the block containing `kissStop()` is never
entered again. The unauthenticated listener stays bound, an attached client stays connected
(its frames merely stop being read), while `--info` reports KISS off. Only a reboot closes it.
This faithfully copies a pre-existing hole in the `bNETCONSOLE` block — but net console is
HMAC-authenticated, KISS is not, so the copy lands harder. Fix: call `kissStop()` (and arguably
`stopNetConsole()`) outside the outer service guard.

**F4 — `{` anywhere in a message body truncates the message**
`src/kiss_functions.cpp:400-409` · verified
The APRS message-number extractor uses `strrchr(text, '{')` with no positional anchor. A client
sending `:DH1FR-1  :set {gain} to 5` gets `set ` injected into the mesh, the rest destroyed, and
a bogus ack-map entry stored. Anchor the scan to the end of the info field per APRS 1.1
(`{` + 1–5 chars at end of string).

### Medium

**F5 — Wrong destination field once `--via` is in the RF path**
`src/kiss_functions.cpp:218-221` and `:112` · confirmed by two independent finders + verifier
`buildAx25()` cuts `msg_destination_path` at the _first_ comma and `ackmapRewrite()` compares
the full path string. When the **last RF transmitter** of a frame (originator or final relay —
each relay re-stamps its own via, `via_functions.cpp:102-104`, `lora_functions.cpp:1254-1256`)
has `--via` set, the path arrives as `"<via>,<dest>"`: the client sees DMs addressed to the via
relay, ACK/REJ frames become double-addressed garbage (the preformatted detector at :225-233
fails), broadcasts render as DMs to the via call, and the v1.3 ack rewrite never fires. The KISS
node's own config is irrelevant — the trigger is outside the operator's control. Two-line fix:
use `msg_destination_call` (`aprs_functions.cpp:325`) in both places; repairs all cases.

**F6 — Stale client socket can block the single client slot indefinitely after WiFi loss**
`src/kiss_functions.cpp:552-604, 625` · code-certain; lwIP timeout behavior "likely"
No teardown on WiFi loss (`kissLoop()` just early-returns; `s_started` stays latched) and no
liveness probe on the client fd. A peer that vanishes without FIN (AP reboot, DHCP change) keeps
`s_client_fd >= 0` for the full TCP retransmit timeout or forever — `accept()` is never called,
so no new client can connect. Combined with F3, the recovery path (`--kiss off/on`) may itself
be unavailable. Fix shape: `kissStop()` on WiFi-loss transition + periodic `MSG_PEEK` probe
(net_console already demonstrates the probe).

**F7 — No rate limit on TX injection; each accepted frame triggers a full NVS rewrite**
`src/kiss_functions.cpp:606-622`, `src/loop_functions.cpp:3559` · verified
Any LAN host (no auth) can drive `sendMessage()`/`sendInjectedPosition()` at TCP line rate; one
256-byte `recv()` can chain ~10 injections, each with a `save_settings()` — a 131-key NVS
rewrite (multi-ms, blocking the loop task and thus LoRa RX) — plus a TX-ring entry (airtime
flooding under the operator's own callsign). Existing injection paths have a human at a prompt
as the natural rate limiter; KISS removes it. Mitigation shape: per-second inject cap +
lazy/periodic `node_msgid` persistence.

**F8 — No authentication, no idle timeout on port 8001**
`src/kiss_functions.cpp:3, 552-604` · design trade-off, stated in the PR
Anyone on the LAN reads the full mesh traffic; the TX gate (base-callsign match) relies on
public information; a single squatting connection locks out the legitimate client permanently
(single-client server, no timeout). Inconsistent with the HMAC-protected net console on the same
firmware. At minimum: document; better: optional netconsole-style auth and an idle timeout.

**F9 — The documented `::text` broadcast form injects a spurious leading colon**
`src/kiss_functions.cpp:394-398` + `docs/kiss_tcp_protocol.md` §5 · verified by trace
`::text` → `text = ":text"` → `out = ":::text"` → `sendMessage()` strips two colons → on-air
payload `":text"`. Every broadcast sent in the doc's own recommended short form carries a stray
`:` (the long form `:*        :text` is handled correctly).

**F10 — TCP backpressure produces corrupt frames instead of dropped ones**
`src/kiss_functions.cpp:124-133, 137-158` · code-certain
`kissRawSend()` silently drops the unsent remainder of a chunk on EAGAIN, but `kissWrite()`
continues with the following chunks and the closing FEND. A slow client receives one
FEND-delimited frame with a hole — decoded as _valid-looking wrong data_ (wrong calls, wrong
info; a truncated TX-result frame can be misread as a different status code). On send failure,
suppress the rest of the frame including the closing FEND, and treat hard errors as disconnect.

**F11 — Inbound frame validation gaps: unterminated address walk, control/PID unchecked**
`src/kiss_functions.cpp:342-353, 368` · code-certain
The address walk exits on a 10-address cap without requiring the extension bit, then
control/PID are skipped unconditionally. Connected-mode AX.25 frames (SABM, I-frames — emitted
by any Linux `axcall` user) have no PID or a 2-byte control field, so the info field is
misaligned and the misparsed remainder can be injected under the operator's callsign (callsign
gate still applies; memory-safe throughout). Reject `ctrl != 0x03 || pid != 0xF0` and require a
terminated address field.

**F12 — "Preformatted" addressee heuristic can emit non-spec frames**
`src/kiss_functions.cpp:225-243` · code-certain
The heuristic fires on any payload whose text before the first `:` equals the addressee — e.g. a
DM to `OE1ABC` with text `OE1ABC: hi` yields info `:OE1ABC: hi` (addressee not 9-char padded).
Dire Wolf/aprslib/APRSdroid reject that as a malformed message. Only treat payloads as
preformatted when `payload[9] == ':'`, or always re-pad.

**F13 — T5-EPAPER is the one target where the queue race is real**
`src/kiss_functions.cpp:491-549`, `src/t5-epaper/peri_lora.cpp:171` · verified chain
On mainstream ESP32, `OnRxDone()` runs synchronously in the loop task (`esp32loop → checkRX`;
the codebase documents this itself in `loop_functions_extern.h:229-232`) — producer and consumer
of the 2-slot queue are the same task and the drop-oldest overwrite is benign. On
`BOARD_T5_EPAPER` the radio runs in `lora_task` (prio ~23, preempts the loop task): torn frames
under `decodeAPRS`, and RSSI/SNR are re-read from the slot _after_ the AX.25 frame was already
streamed out (`:538`), so RxMeta can describe a different packet. Aggravated by e-paper refresh
stalls. Not in `default_envs`, so field exposure is small. Fix: snapshot the slot (or at least
rssi/snr + buflen) before processing. Note: the header comment (`kiss_functions.h:28-30`,
"runs in the radio callback / timer task") is inaccurate for ESP32 and should be corrected.

**F14 — HEY frames waste the 2-slot queue**
`src/lora_functions.cpp:769-779` + `src/kiss_functions.cpp:251-254` · verified
`queueKiss()` is called for TEXT, POSITION **and HEY**, but `buildAx25()` discards HEY. In a
busy mesh, periodic HEY frames evict queued text/position frames from the 2 slots before they
are converted — silent frame loss to the client. One-line fix: don't queue HEY.

**F15 — No automated tests for an untrusted-input parser**
The repo ships a native Unity harness (`test/`, `env:native_extradio`) built for exactly this
kind of pure-logic code, and the KISS deframer, `ax25Addr`/`ax25DecodeCall`, `baseCallMatches`
and the ack map are all natively testable. The PR adds zero automated tests; `docs/kiss_tcp_test.md`
is connection-setup-oriented and its "Verified" section is frozen at the v1.0 feature set (the
v1.1–v1.3 features — position injection, callsign gate, TX-result frame, ack rewriting — are
claimed verified only in commit/PR prose).

### Low (selected)

- `nrf52/nrf52_ble.cpp:25` — stale extern declaration of the old `sendMessage` signature (unused
  today; becomes a link error the day someone calls it). Remove.
- `src/kiss_functions.cpp:423` — `ackmapPut()` also fires for group/broadcast injects, whose
  entries can never be consumed (no `{NNN` appended for non-DM) and evict live DM mappings from
  the 8-slot ring.
- `src/kiss_functions.cpp:645-654` — `kissStop()` clears the ack map but not the RX queue; after
  an off/on cycle, up to two stale frames (with stale RSSI/SNR) can be delivered.
- Queue drained in index order, not arrival order — occasional 2-frame reordering to the client
  (inherited byte-for-byte from `flushExternQueue`).
- `sendInjectedPosition()` (`loop_functions.cpp:3561-3572`) registers the msg_id in own-TX/dedup
  structures before `addTxRingEntry()` whose return value is ignored — the `0x01 OK` TX-result
  is not actually derived from successful queueing (same shape as pre-existing `sendMessage`).
- `sendInjectedPosition()` passes `addLoraRxBuffer(id, false)` where the mirrored sequences pass
  `true` on gateway nodes — currently without a live consumer for positions (the `bserver` flag
  only feeds binary-ACK forwarding), but it silently breaks the "mirrors SendAckMessage"
  invariant the comment claims; worth aligning.
- KISS clients never see the node's own transmissions or any locally originated traffic
  (`queueKiss` taps only new RF receptions) — defensible design, but undocumented; an attached
  client cannot monitor its own digipeated traffic.
- Ethernet-only boards (T-ETH-ELITE, T-Connect-Pro) and AP mode never start KISS
  (`WiFi.status()` guard) while ext-udp works there — document or extend.
- `docs/kiss_tcp_protocol.md` — the claim that "standard KISS clients ignore ports 1/15
  automatically" is wrong in general (port-0-command frames on other ports are _routed_, not
  ignored: Dire Wolf logs channel errors, naive monitors render junk). Worth a caveat; the
  RxMeta/TX-result _content_ was verified accurate, including the worked byte examples.
- Doc drift: `docs/kiss_mode_analysis.md` carries stale pre-implementation details;
  `kiss_tcp_protocol.md` §6 "silently dropped" contradicts the `0x02` result code (stale v1.1
  text); text-length limit (160 minus addressee overhead → `0x04`) undocumented.
- The `CLAUDE.md` hunk changes the contributor-facing PR-language rule (German → English) inside
  a feature PR — for the upstream maintainer to judge.

## 5. Refuted claims (checked and dismissed — do not re-report)

- **"`kissLoop()` runs only once per 5 minutes"** — false. The `web_timer` block closes at
  `esp32_main.cpp:3785`; the netconsole/KISS/extudp blocks after it execute every loop iteration
  (verified by brace-level analysis). KISS connection handling is exactly as responsive as the
  net console.
- **"`queueKiss` races with `flushKissQueue` on ESP32"** — same task on all mainstream targets
  (see F13); the race exists only on T5-EPAPER.
- **"The 255-byte memcpy in the radio callback endangers the callback stack"** — the copy
  targets a static slot; frame cost is a pointer.
- **"The 2-slot KISS queue is a downgrade from the extern queue"** — `MAX_EXTERN_QUEUE` is also
  2; the pattern is an exact mirror.

## 6. Verified-correct highlights

Positive results worth stating, because they were actively attacked and held:

- **Memory safety of the inbound parser**: every length/index derived from the TCP stream is
  guarded (underflow-safe `size_t` arithmetic, clamped memcpys, bounded address decode); fuzzing
  the deframer by hand-analysis found no out-of-bounds path.
- **KISS framing**: SLIP escaping complete and correct in both directions, escape state safe
  across `recv()` boundaries, oversize recovery correct, standard KISS command frames correctly
  ignored.
- **AX.25 encoding**: address layout, C-bit/H-bit conventions, extension-bit placement, UI
  control/PID, digi-path derivation and the output-size guard all conform (Dire Wolf/YAAC will
  accept these frames).
- **Ack-number arithmetic**: `msg_id & 0x3FF` ↔ `{%03i` ↔ `ack%03i` round-trip is exact
  (`node_msgid` ≤ 999 < 1024, no aliasing).
- **No command injection**: the `":{ADDR}text"` construction makes `commandAction()` unreachable
  from the KISS path; `baseCallMatches()` edge cases (empty calls, bare `-7`, case tricks) all
  reject correctly.
- **Integration ordering**: `queueKiss()` sits post-dedup next to `queueExtern` — no self-echo,
  no duplicate taps; `sendMessage()` default-arg change is correct C++ and all existing callers
  verified; WiFi-keepalive gating mirrors the netconsole precedent.
- **`--kiss` command block**: prefix-match ordering, sset4 bit handling, web setparam/getparam
  plumbing and status output all verified correct.
