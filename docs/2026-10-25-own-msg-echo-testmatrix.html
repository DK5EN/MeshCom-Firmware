Own-message echo release: test matrix and expected outcomes

MeshCom firmware, fork-dev eb246050, nodes on 4.40a builds of 2026-10-24. Prepared 2026-10-25. Cases, expected outcomes and log patterns, with the observed results of the bench run on 2026-10-25.

BLUF
  • Reproduced on the bench 2026-10-25: DK5EN-98 to group 9999 released 9 of 10 own texts before its own TX; with the competing bench gateways airgapped 0 of 10. Own PNs 0 of 20. Observed column below.
  • Bug: an own group or * text on a gateway is released (slot DONE, length 0) before its first own LoRa TX, because another gateway transmits the server copy first and the originator takes that echo as "already on air".
  • Scope: group texts and *: yes. Own PN: no (ACK_SKIP_READY, the slot stays READY and is sent). A non-gateway originator has no server shortcut and is not affected.
  • Evidence (DK5EN-98 logger 2026-10-24 16:21 to 2026-10-25 11:24, organic traffic, no test sends): group 20: 49 of 82 own texts released before own TX; *: 1 of 4; PN: 0 of 26. Other groups: 0 of 6.
  • Goal rule: a message from my node goes out on LoRa at least once. An echo heard after that stops further repeats (one-time send). An echo may stop retries, never the first transmission.
  • Plan: 8 executable cases (E1-E8, N = 10 each, unique marker per message) on group 9999, group TEST and PN between own bench nodes; 4 theory cases (T1-T4) are never sent.

1. Mechanism

On a gateway the server upload is queued in the same call that writes the ring slot (immediate, for group, * and PN). The LoRa side waits for the running CSMA window (0-4.85 s plus re-arms). Another gateway that gets the server copy queues it as udp_rx (status DONE) with no destination filter and may reach the air first. The originator hears that echo while its own slot is still READY and releases it.

Code locations (fork-dev eb246050)

  • Own text entry: sendMessage() src/loop_functions.cpp:4278; ring write READY, src=user_msg :4660; server upload queued in the same call :4755 (addNodeData).
  • Server text at a gateway: src/esp32/udp_frame_esp32.cpp:611-620 -> gwUdpRxEnqueue -> addTxRingEntry(..., RING_STATUS_DONE, "udp_rx"). No destination filter on the LoRa side: *, any numeric group (own group list not consulted), named group TEST and PN to a foreign call all go on LoRa. Only a PN to the gateway's own call is not put on LoRa (:386-402, displayed and ACKed).
  • Echo release: src/lora_functions.cpp:1090-1117; predicate pnFrameIsReleasableGroupText() src/pn_retry.h:362 (text frame, not an own PN, not an own RM1 command).
  • PN retry ladder after SENT: src/lora_functions.cpp:3290-3420 (echo restarts the 40 s wait, [RETX] PN echo, wait restarted; 3 copies). findAndStopRingSlotImpl skips READY slots.
  • Which gateways receive a given server text is decided by the server (subscription), not by the firmware.
  • Log gap: [RETX] echo on READY slot, released retid:N (bDisplayRetx) carries no msg_id; the next checkOwnTx:<id> line with the same timestamp has it. TX-UDP is printed at ring write, not on LoRa; TX-LoRa / [MC-DBG] RING_TX_READ is the real TX marker.

3. PN (private messages)

DK5EN-98 to DK5EN-1 (E4)

  • -98 writes the ring slot READY and uploads at once. LoRa waits for the CSMA window.
  • -1 gets the UDP copy: PN to its own call is displayed and ACKed, not put on LoRa.
  • Other gateways put a PN to a foreign call on LoRa (no destination filter). If one transmits first and -98 hears it: [MC-DBG] ACK_SKIP_READY, the slot stays READY and is sent.
  • -98's own LoRa copy reaching -1 is the second copy with the same msg_id: dedup drop, no second ACK.

DK5EN-1 to DK5EN-98 (E5)

  • -1 writes READY, uploads at once, sends its own LoRa copy.
  • -98 gets the UDP copy: own call, not put on LoRa, displayed and ACKed (organic log: 47 PN to DK5EN-98 received, 0 on LoRa).
  • A later copy via LoRa with the same msg_id: dedup drop, no second ACK.

Rules that hold for both

  • Own PN is never released by an echo (pnFrameIsReleasableGroupText() excludes it). Organic: 26 of 26 sent, 1 x ACK_SKIP_READY.
  • An ACK never stops an unsent READY PN: findAndStopRingSlotImpl skips READY slots. The PN is always sent at least once.
  • After SENT: an echo restarts the 40 s wait ([RETX] PN echo, wait restarted), retry ladder of 3 copies; server :ack / binary ACK stop it.
  • First copy (UDP or LoRa) displays and ACKs (LoRa one-shot + UDP); later copy with the same msg_id is a dedup drop.
  • Organic: PN to OE5PYB-1 was put on LoRa by -98 as a server frame 8 times.
