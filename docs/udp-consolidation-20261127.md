# UDP receive handler consolidation (analysis, 2026-11-27)

Scope: merge `handleUdpFrame_esp32` (`src/esp32/udp_frame_esp32.cpp`, 807 lines) and
`handleUdpFrame_nrf52` (`src/nrf52/udp_frame_nrf52.cpp`, 784 lines) into one implementation, with
a pure parse core for the later bounded proof. Operator decision 2026-11-27. Analysis only, no code
changed. Tree state read: `fork-dev` @ 770764e5 plus the uncommitted edits listed in `git status`
(none of them in the files below). E = ESP32 file, N = nRF52 file, line numbers are those files.

Evidence rules: every drift claim was checked on both sides. Commits cited were checked with
`git branch --contains` (all on `fork-dev`) and `git log --grep=Revert` (none reverted). Anything
not checked is marked "not verified". No build, test or bench run was made for this document.

## 0. Result in six lines

- Common logic is about 72 percent of the code lines (comments and blanks stripped, line LCS);
  the text branch, ACK/STO/RM handling, relay enqueue and CONF parse are identical modulo
  whitespace and comments (`diff -w -B`).
- 12 platform differences (P), 6 drift items (D), 14 cosmetic ones (C).
- 4 of the 6 D items change behaviour on one platform if merged (D1, D2, D3, D5); D4 and D6 are
  narrow or hazard-only. D3 is the one the operator must see: nRF52 gateways never show or act on
  server-delivered DM/group text (display, `{ping}/{pong}/{MCP}`) today, ESP32 does.
- The existing twin and goldens do not see D1, D2, D3: the test runs `bGATEWAY=false` (a state an
  nRF handler never runs in), no test feeds a GATE frame of unknown type for liveness, and no test
  inspects the dedup ring for a vetoed position.
- Design: one shared `src/udp_frame.cpp` (`handleUdpFrame`), a pure core
  `src/udp_frame_parse.{h,cpp}`, 5 platform hooks in `src/udp_frame_platform.h`, 2 tiny
  per-platform hook files. Net production code about -690 lines.
- Send twin: merge in a separate, later wave. Gateway service twin: do not merge (pinned
  both-valid, DR-14/DR-15).

### 5.3 Pure parse core (the proof target)

Header `src/udp_frame_parse.h`:

```cpp
enum UdpFrameClass { UDPF_REJECT_ZEROS = 0, UDPF_GATE, UDPF_CONF, UDPF_BEAT, UDPF_OTHER };
enum UdpGateKind   { UDPG_NONE = 0, UDPG_TEXT /*0x3A*/, UDPG_POS /*0x21*/, UDPG_HEY /*0x40*/, UDPG_UNKNOWN };
struct UdpFrameInfo {
    uint8_t  cls;           // UdpFrameClass
    uint8_t  gate_kind;     // UdpGateKind; UDPG_NONE unless cls==UDPF_GATE and gate_len>0
    uint8_t  msg_type;      // buf[UDP_MSG_INDICATOR_LEN] if gate_len>0, else 0
    uint8_t  conf_size_ok;  // 1 iff cls==UDPF_CONF and UDP_MSG_INDICATOR_LEN <= len <= UDP_CONF_BUFF_SIZE
    uint16_t gate_len;      // len-4 for len>=4 (never needs the old clamp for len<=255), else 0
    uint8_t  zero_run;      // the old zerocount
};
uint8_t udpFrameZeroRun(const uint8_t *buf, size_t len);                  // E:91-101 / N:88-98
void    udpFrameClassify(const uint8_t *buf, size_t len, UdpFrameInfo *out); // precondition len <= UDP_TX_BUF_SIZE
```

Decides: (1) too-many-zeros verdict (`zero_run > MAX_ZEROS`), (2) indicator class with a `len>=4`
requirement (today the 4 bytes are compared whatever `packetSize` is), (3) GATE payload span and
type class, (4) CONF size bound. Touches no globals; reads only the constants
`UDP_TX_BUF_SIZE` (configuration_global.h:303), `UDP_CONF_BUFF_SIZE` (:304),
`UDP_MSG_INDICATOR_LEN` (:306), `MAX_ZEROS` (:400). Loops: one, `i+1 < len`, at most 127 iterations
for `len<=255`, constant bound for BMC; plus a 4-byte compare. The registration early return
(`gwRegFrameIsOther`, gw_reg_state.h) stays in the shell, ahead of the classify call, as today.

Facts the proof can establish (all derived from the present code, not run):

- `zerocount` is `uint8_t`; max value for `len<=255` is 254 (127 pairs), so it cannot wrap; the
  rule is "number of zero bytes in the trailing run of aligned zero pairs", an odd last byte is
  not scanned, a run starting at an odd index needs 9 zeros to exceed `MAX_ZEROS=6`.
- The `gate_len > UDP_TX_BUF_SIZE` clamp (E:126-127, N:131-132) is unreachable for `len<=255`
  (`len-4<=251`). Callers bound `len`: E reads at most `UDP_TX_BUF_SIZE-1` (udp_functions.cpp:183),
  N accepts `packetSize <= UDP_TX_BUF_SIZE` (nrf_eth.cpp:516).
- No read of `buf[4]` when `len==4` and no indicator compare when `len<4` (D5, closes today's
  stale-byte read).

Later candidates, not in this wave: `parseConfFrame` (`conf_frame.cpp`, already pure) and a second
core `udpTextRoute()` (the dest/ack/rej/`{NNN`/group decision at E:392-421, about 60 lines of plain
`strcmp` logic) so the text branch becomes a table of flags. `decodeAPRS` (aprs_functions.cpp:172)
is a separate, larger target; feasibility not assessed.
