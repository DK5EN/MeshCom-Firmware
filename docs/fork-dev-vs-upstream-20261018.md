# MeshCom firmware: fork-dev compared with upstream/dev (18 October 2026)

Two complete sections follow, German first, then English. Both hold the same content. The table lists what the fork branch `fork-dev` contains compared with `upstream/dev` of icssw-org/MeshCom-Firmware.

## Deutsch

### Kurzfassung

**Ergebnis: `upstream/dev` enthält nichts, was `fork-dev` nicht auch enthält. `fork-dev` bringt zusätzlich eine Reihe von Funktionen und Fehlerbehebungen mit, die noch nicht im Upstream-Zweig stehen.**

- Firmware-Update für ESP32: Der Knoten prüft GitHub-Releases per HTTPS und meldet neue Versionen. Die automatische Installation lässt sich nicht einschalten (herausgebaut). Die manuelle Installation ist möglich.
- Safeboot (der Update-Starter der ESP32-Knoten) ist versioniert, nimmt komprimierte Uploads an und nennt die echten Fehlergründe.
- Fernwartung über LoRa mit signierten Direktnachrichten, standardmäßig aus, benötigt das Knoten-Passwort. Dazu eine Web-Seite „Remote“ mit drei gespeicherten Knoten.
- Gateway-Zwischenspeicher: Ein Gateway nimmt auch vom Server kommende Direktnachrichten in sein Postfach. Die Meldung der Postfach-Rufzeichen an den Server ist fertig, aber in Release-Builds fest abgeschaltet, bis der zentrale Server sie auswertet.
- GPS-Positionsfilter (Kalman-Filter mit Bewegungserkennung und Raster-Halten), standardmäßig an.
- LED: Fern-Steuerung der Board-LED (an, aus, blinken) und der Lade-LED.
- Diagnose: Laufzeit der Empfangsverarbeitung in der STAT-Zeile, größerer Sendepuffer der Konsolen-Schnittstelle (Ausgaben bremsen den LoRa-Empfang nicht mehr).
- Korrekturen nur im Fork: Prüfung der `--via`-Liste, Netz-Konsole (Port 2323), mehrere Build-Verbesserungen.
- Außerdem nur im Fork, ohne Firmware-Bezug: 72 Host-Testumgebungen, Bench- und Log-Werkzeuge, Dokumentation, CI-Release-Pipeline, Web-Flasher.

### Hinweise zu einzelnen Punkten

**Automatische Update-Installation: wo „auto“ abgelehnt wird.** Der Programmteil für die automatische Installation ist nicht mitkompiliert und lässt sich weder per Build-Schalter noch per Einstellung aktivieren.

- Web-Seite (Auswahl und `setparam`): lehnt „auto“ und „off“ ab. Die Auswahl bietet nur „notify (prod)“ und „notify (dev)“, „auto“ erscheint ausgegraut.
- Konsole und BLE (`--autoupdate auto`): lehnen „auto“ in jedem Build ab (`[ERR];locked;autoupdate`). „off“ wird ebenfalls abgelehnt.
- Konfigurationsimport: akzeptiert den Wert 2 (Bereich 0 bis 2), damit alte Sicherungen einlesbar bleiben, und setzt ihn sofort auf „notify“ (1). Ein gespeicherter Wert 2 oder 0 wird beim Laden ebenfalls zu „notify“.
- Fernwartung: kennt keinen Befehl dafür.
- Ein ausdrücklich ausgelöster Fernwartungsbefehl `upd go <Version>` lädt die genannte Version und installiert sie. Das ist keine automatische Installation, aber eine Fernauslösung durch einen signierten Befehl, unabhängig vom eingestellten Modus.

**Fernwartung: Befehlsgruppen.**

- Aktionen: Neustart, Status, Position senden, Track senden, Zähler abgleichen (sync).
- Schalter: GPS, Track, Display, LED (an, aus, blinken), Gateway, Mesh.
- Parameter: Sendeleistung (im Bereich des Boards), Ausgänge (Port-Expander a0 bis b7), Lade-LED (auto, an, aus).
- Abfragen: Funkeinstellungen, Sensoren, Sendewarteschlange, Postfach, maximale Hops, MHeard-Liste (Zeile oder Rufzeichen), Netzwerk.
- Lesen und Schreiben: Knotenname, APRS-Text, Position.
- Update: Status abfragen, Prüfung auslösen, `go <Version>`.

**Postfach-Meldung an den Server (`--stor`).** Die Meldung ist fertig eingebaut und in Release-Builds fest aus: `--stor on` wird abgelehnt (`[ERR];locked;stor`), Konfigurationsimport und Start setzen den Wert auf aus. Nur Instrumentierungs-Builds für den Prüfstand können sie einschalten. Sie wird freigegeben, sobald der zentrale Server die Meldung auswertet.

**GPS-Filter: Boards.** Der Filter sitzt in der gemeinsamen GPS-Schleife. Er läuft auf allen Boards mit eingebautem GPS-Pfad über diese Schleife: ESP32-Boards mit GPS sowie Heltec T114 und T-Echo (nRF52). RAK4631 (eigener GPS-Pfad) und T-Deck Pro (eigener GPS-Task) lesen die Position an der Schleife vorbei und haben den Filter noch nicht; `--gpsfilter` meldet dort „no position filter on this board“ (RAK4631) oder hat keine Wirkung (T-Deck Pro).

**Web-Anfrage-Schutz.** Mit dem Standard `MC_WEB_GUARD=0` bleibt das Verhalten für alle übrigen Adressen wie im Upstream-Zweig.

## English

### Summary

**Outcome: `upstream/dev` contains nothing that `fork-dev` lacks. `fork-dev` adds a set of features and bug fixes that are not in the upstream branch yet.**

- Firmware update for ESP32: the node checks GitHub releases over HTTPS and announces new versions. The automatic-install mode cannot be switched on (compiled out). Manual installation works.
- Safeboot (the update starter of ESP32 nodes) is versioned, accepts compressed uploads and reports the real failure reasons.
- Remote management over LoRa with signed direct messages, off by default, needs the node password. Plus a web page "Remote" with three saved nodes.
- Gateway store-and-forward: a gateway also takes direct messages that arrive from the server into its mailbox. The announcement of the mailbox callsigns to the server is implemented but fixed off in release builds until the central server evaluates it.
- GPS position filter (Kalman filter with motion detection and grid hold), on by default.
- LED: remote control of the board LED (on, off, flash) and of the charge LED.
- Diagnostics: receive-handler timing in the STAT line, larger console UART send buffer (prints no longer stall LoRa reception).
- Fixes only in the fork: validation of the `--via` list, net console (port 2323), several build improvements.
- Also fork only, not firmware: 72 host test environments, bench and log tools, documentation, CI release pipeline, web flasher.

### Notes on individual items

**Automatic firmware install: where "auto" is rejected.** The code for the automatic install is not compiled in and cannot be activated by a build flag or a setting.

- Web page (selection and `setparam`): rejects "auto" and "off". The selection offers only "notify (prod)" and "notify (dev)"; "auto" appears greyed out.
- Console and BLE (`--autoupdate auto`): refuse "auto" in every build (`[ERR];locked;autoupdate`). "off" is refused as well.
- Configuration import: accepts the value 2 (range 0 to 2) so old backups stay importable, and sets it to "notify" (1) right away. A stored 2 or 0 also becomes "notify" on load.
- Remote management: has no command for it.
- An explicitly sent remote command `upd go <version>` downloads the named version and installs it. This is not the automatic install, but it is a remote trigger by a signed command, independent of the configured mode.

**Remote management: command groups.**

- Actions: reboot, status, send position, send track, counter sync.
- Switches: GPS, track, display, LED (on, off, flash), gateway, mesh.
- Parameters: TX power (within the board range), outputs (port expander a0 to b7), charge LED (auto, on, off).
- Reads: radio settings, sensors, TX queue, mailbox, maximum hops, MHeard list (row or callsign), network.
- Read and write: node name, APRS text, position.
- Update: read status, trigger a check, `go <version>`.

**Mailbox announcement to the server (`--stor`).** The announcement is built in and fixed off in release builds: `--stor on` is refused (`[ERR];locked;stor`), configuration import and boot force it off. Only instrumented bench builds can switch it on. It will be enabled once the central server evaluates the announcement.

**GPS filter: boards.** The filter sits in the shared GPS loop. It runs on every board that reads its GPS through that loop: ESP32 boards with GPS and Heltec T114 and T-Echo (nRF52). RAK4631 (own GPS path) and T-Deck Pro (own GPS task) read the position past that loop and do not have the filter yet; `--gpsfilter` answers "no position filter on this board" on the RAK4631 and has no effect on the T-Deck Pro.

**Web request guard.** With the default `MC_WEB_GUARD=0`, behaviour for all other addresses is the same as in the upstream branch.
