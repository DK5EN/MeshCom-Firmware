# RCA PONG-RX-01: DK5EN-1 "never registered the pongs" (2026-11-08)

BLUF: the premise does not hold. DK5EN-1 registered 4 of 4 pongs the RAK sent. The Heltec OLED shots of the very run
show `PONG 159`, `PONG 158`, `PONG 156`, `PONG 155` with RSSI/SNR and a round-trip time. The negative number in
`{pong}{-366632159}` is harmless: the Heltec parses nothing numeric. The only anomaly in the run is ping #3, which the RAK
dropped as a dedup duplicate (`DUP:d`), so it sent no pong and the Heltec drew `PONG ... FAILED`, correctly. Analysis only;
no source, tool or test file was changed.

Five pings, four pongs, four `PONG` frames, one `FAILED`. The "SENT for ~158 s, never PONG" impression has a mechanical
cause: every `PONG` frame is held for `node_pingtime` s (`loop_functions.cpp:2829-2830`, `DisplayOffWait`), and the next ping
overwrites it (`sendPing` draws `SENT` at `loop_functions.cpp:4188-4195`). The last frame hold ends ~30 s after the last
pong (+125 s) = ~155-158 s, where the clock page returns (shot 021). A `PONG` frame is on screen a few seconds before the
next `SENT`; a sparse look at the OLED sees mostly `SENT`.

## Q1: signed/unsigned (`{pong}{-366632159}`): REFUTED as a cause

- Types: `aprsMessage::msg_id` is `unsigned int` (`aprs_structures.h:64`), `SendPong(String, unsigned int msg_id)`
  (`loop_functions.h:124`). `SendPong` prints it with `"{pong}{%03i}"` (`loop_functions.cpp:4251`), i.e. `%i` on an unsigned
  value: ids >= 2^31 print negative. `_GW_ID & 0x3FFFFF` shifted by 10 (`:4145`) fills 32 bits, so half of all nodes have
  negative ids. `0xEA25A321` = -366632159 as int32 matches the RAK log exactly.
- The pong carries the PING's id (`lora_functions.cpp:1913`: `SendPong(source_call, aprsmsg.msg_id)`), not its own.
- Pong handler (`loop_functions.cpp:2806-2831`): no `atoi`/`strtoul`, no compare with the stored ping id. It takes
  `msg_payload + 14` (`:2814`) and prints `%.3s`. RX path (`lora_functions.cpp:1920-1938`): `{pong}` to our call ->
  `queueDisplayText`, `addBLEOutBuffer`, `bPingSend = false`. Nothing matches ids at all; any `{pong}` to us clears the wait.
- The 3 digits agree by construction: `sendPing` shows `cmsg[7..9]` of `"%i"` of its id (`:4190-4192`), the pong handler shows
  chars 7..9 of the same decimal string inside the payload (`payload+14` = `"{pong}{"` 7 + index 7). Shots confirm `159`/`159`.
- Per platform: ESP32 and nRF52 are both 32-bit `int` (no `long` difference), both run the same `SendPong`/`sendDisplayText`
  (shared TUs); RAK (nRF52) -> Heltec (ESP32) was proven by the shots; ESP32->ESP32 and nRF52->nRF52 print the same string.
  Hypothesis (not bench-tested): the digit-position coupling breaks for decimals shorter than 8 characters (small `_GW_ID`):
  the strlen guard (`:2814`) shows `""`, cosmetic only.

## Q2: addressing and dedup: no drop on the Heltec

- Pong is `DK5EN-90>DK5EN-1` (`:4247-4248`, dest = ping source), the Heltec's own call: `strcmp(destination_call, node_call)`
  (`lora_functions.cpp:1899`) passes. "via:DK5EN-1" in the RAK log is the PING's `msg_source_path` printed by the RAK
  (`:1909`), not a pong routing field. Mesh-off does not gate this branch (it only gates relay, `bMeshDestination`).
- Heltec dedup keys on the pong's own id (`91A4340B...`, unique, `is_new_packet` `lora_functions.cpp:594`). Not a candidate.

## Q3: could the Heltec have missed it? Not in this run

RX is proven by the `PONG` frames (they are drawn only from `sendDisplayText`, reached only via `lora_functions.cpp:1930`).
The CAD_BUSY runs earlier that day delay TX only and are unrelated. To tell the cases apart on a future run, capture the
Heltec serial (bDisplayInfo on): a `[PONG] from:DK5EN-90 to:DK5EN-1` line (`lora_functions.cpp:1926`) = RX + addressing
ok; `RX_DEDUP_DUP msg_id=91A4...` instead = dedup (Q2); neither line, but RAK `TX-LoRa ... {pong}` = RF loss/CAD (Q3).

## Q4: why pinging stops after 5

`--ping start` sets `node_pingcount = node_pingmax`, default `PING_MAX` = 5 (`command_functions.cpp:4441-4452`,
`configuration_global.h:312`; release builds clamp pingmax to 5, `prod_lock.h:172`). ESP32 loop sends while
`node_pingcount > 0` and decrements per attempt (`esp32_main.cpp:5590-5614`). Ids 321..325 = exactly 5 pings. The first
ping fires at once (`resendPing` is stale, `:5587`).

## The one real anomaly: ping #3 `EA25A323` dropped as dup on the RAK

RAK log `:1018`: `RX_DEDUP_DUP msg_id=EA25A323 slot=3`. The ring (100 slots, `configuration_global.h:353`) already
held that id; the add of `EA25A324` then lands in slot 3 (`:1169`). Ids `EA25A320`..`22` were new. Cause = id replay inside the
dedup window; the Heltec counter wraps at 999 and burns 100 per boot (`msgid_counter.h:49`, `:53`).
HYPOTHESES (unproven; the log holds no earlier `ADD EA25A323` since it starts 15:11:37):
(a) id 803 was used one lap (1000 ids) earlier and the RAK heard it; (b) a previous Heltec boot replayed 800.. because its
load write-back failed (`esp32_flash.cpp:397`, would print `[SETST];counters;load_writeback;failed`).
Bench check: Heltec `--msgid` twice across a reboot (must jump by >= 100, `[SETST];counters;msgid;N`), RAK `grep
RX_DEDUP_ADD.*EA25A323` over the earlier day's RAK logs. Not a PONG-RX defect; no fix proposed until (a)/(b) is decided.

## Side findings (both verified on the current tree)

1. nRF52 has no ping budget: `nrf52_main.cpp:2883-2905` checks only `node_pingtime > 29` and `node_pingcall`; it never reads
   `node_pingcount` (ESP32 does, `esp32_main.cpp:5590`) and has no `[PONG]...fail`/`PongFail` branch. `--ping stop`
   (`command_functions.cpp:4464`) and `--pingmax` are ignored on nRF52; it pings every `pingtime` until `--pingtime 0`.
2. `node_pingduration` (`loop_functions.cpp:2821`) is overwritten in place; a second `{pong}` for one ping computes garbage
   (cosmetic, a dup is normally dedup-dropped first).

## Fix proposal (minimal, for side finding 1; PONG-RX itself needs none)

- New `src/ping_budget.h` (pure C++): `static inline bool pingBudgetOpen(int pingtime, const char *call, int count)` =
  `pingtime > 29 && call[0] != 0 && count > 0`. Use it in `esp32_main.cpp:5590` (same semantics) and in `nrf52_main.cpp:2885`
  with `node_pingcount--` after `sendPing` (same exclusions: `PING_SUPPRESSED_TRACK`, `PING_INVALID_TARGET`,
  `esp32_main.cpp:5613-5614`). Default budget: `ping start` already fills it. Wire format unchanged.
- Do not change `{pong}{%03i}` (`:4251`): peers' display parsing is positional; `%u` would change the width of the
  digit string and the `payload+14` window.
