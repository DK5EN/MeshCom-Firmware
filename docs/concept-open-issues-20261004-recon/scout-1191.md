# Scout report: upstream issue #1191 "AutoReconnect" (fork-dev a9e64cf6, read-only)

BLUF: Firmware already re-advertises immediately on both platforms (ESP32 NimBLE `advertiseOnDisconnect(true)`, nRF52 `restartOnDisconnect(true)`, advertise forever). The reconnect gap is in the app: its reconnect code exists but is commented out ("RECONNECT DISABLED"). Firmware work is hardening and diagnostics: one real stale-state race on ESP32, no HCI reason logging on nRF52, no bonding by design.
Paths below are relative to /Users/martinwerner/WebDev/MeshCom-Firmware-DEV-Main unless marked APP=~/WebDev/Meshcom-MobileApp.

## Findings

### 1. ESP32 (NimBLE)

1.1 Library: `h2zero/NimBLE-Arduino@2.2.3` (platformio.ini:1107, `[esp32libs]`; libdeps library.properties version=2.2.3). Build caps: MAX_CONNECTIONS=1, MAX_BONDS=1, MAX_CCCDS=2, central+observer roles disabled, host task stack 3072, MSYS1 block count 4 (platformio.ini:1149-1155). ATT preferred MTU = lib default 255 (libdeps nimconfig.h:224); app negotiates, no `setMTU` call in firmware.
1.2 Server callbacks: `class MyServerCallbacks` src/esp32/esp32_main.cpp:350-440 (instance `serverCallbacks`). onConnect :351, onDisconnect :380, onConnParamsUpdate :398, onMTUChange :408, onPassKeyDisplay :420, onAuthenticationComplete :433.
1.3 Disconnect today: the LIB restarts advertising, not the firmware. `pServer->advertiseOnDisconnect(true)` esp32_main.cpp:1925 -> NimBLEServer.cpp:418 (libdeps) calls `startAdvertising()` synchronously right after `onDisconnect`. Delay = 0 ms. The old firmware-side restart is commented out (esp32_main.cpp:394 and :3288-3293 "KBC/KFR TEST 2025-04-10", delay(2000)+startAdvertising). Failed-connect path (`BLE_GAP_EVENT_CONNECT` status!=0) also restarts advertising inside the lib (NimBLEServer.cpp:356-361), invisible to the firmware (no callback). Host reset: `NimBLEAdvertising::onHostSync` restarts only if duration==0 (NimBLEAdvertising.cpp:~280), which holds because `pAdvertising->start()` is called without a duration (esp32_main.cpp:1990).
1.4 Advertising params (esp32_main.cpp:1959-1990): `reset()`, name `M<dev>-<mac2>-<call>` via `setName` (cut to 26 chars unless `bBLElong`), connectable undirected + general discoverable (lib default, NimBLEAdvertising.cpp:50-53), interval NOT set -> itvl 0 -> host default fast 30-60 ms (ble_gap.c:2787, `BLE_GAP_ADV_FAST_INTERVAL1_*`; inferred from source, not measured). Address type public (NimBLEDevice.cpp:107). TX power +9 dBm (:1909).
1.5 `bBLElong` (default false; `--blelong`/`--bleshort`, command_functions.cpp:2005-2040, reboots): only in long mode the manufacturer data and the 128-bit NUS service UUID 6E400001-... go into the advert and scan response is on (esp32_main.cpp:1968-1982). In the default short mode the advert carries the name only. Relevant for app-side filtered scans (iOS background scan needs the UUID) but not for connect-by-address.
1.6 Connection parameters: onConnect requests `updateConnParams(handle, 24, 48, 0, 400)` = 30-60 ms, latency 0, 4 s supervision timeout (esp32_main.cpp:377; commit dbd5db9c, OE1KFR 2026-09-26, "was 1.8 s: rejected by iOS, shortened Android's 5 s default"). Supervision timeout of 4 s = worst-case time the node needs to notice a vanished phone; with MAX_CONNECTIONS=1 the node is unconnectable (not advertising) during that window.
1.7 MTU: no node-initiated exchange; `onMTUChange` stores `g_blePhoneStats.last_mtu` (:408-418). Live value via `esp32_ble_mtu()` (:2118-2127). Drain assumes MTU 247 clamps (BLE-N2).
1.8 Security: `setSecurityIOCap(DISPLAY_ONLY)` + `setSecurityAuth(false,false,false)` = no bonding, no MITM, no SC (esp32_main.cpp:1910-1911). All `*_ENC`/`*_AUTHEN` characteristic flags are commented out (:1935-1950), so the node never triggers pairing; the passkey callback (:420-430, `bt_code` or PIN 0) only runs if the phone starts pairing. Nothing is persisted (no bond DB use) -> "keep the bond" has nothing to keep. The PIN is app-layer: hello frame `04 10 20 30` or `23 10 20 30`+SHA-256(6-digit PIN) (src/phone_commands.cpp:293-340); wrong/missing hash sets `ble_disconnect_requested` -> `pServer->disconnect()` in esp32loop (esp32_main.cpp:3280-3284). N-07 (unauthenticated channel) is ACCEPTED/WONTFIX because bonding would drop the app fleet (docs/architecture/08-defect-catalogue.md:379-385, :1815).
1.9 Flags and where they can stay stale (ESP32):

- `deviceConnected` (esp32_main.cpp:308, plain bool, written from the NimBLE host task, no volatile/atomic), set in onConnect :353, cleared in onDisconnect :382.
- FINDING (real, small): the per-session reset of `isPhoneReady`, `g_ble_uart_is_connected`, `bAckInfo`, `config_to_phone_prepare`, `conffin_sent` runs ONLY in esp32loop on the edge `!deviceConnected && oldDeviceConnected` (esp32_main.cpp:3288-3299). If disconnect and reconnect both happen between two loop passes (loop stall, e.g. flash write, OTA, WiFi connect, long TX path; instrument builds measure stalls), the edge is never seen: `isPhoneReady` stays 1 from the old session, so the new central is treated as authenticated/ready BEFORE its hello and PIN check, and the connect branch (:3310) is skipped too (T-Deck BT icon not refreshed). onConnect resets only `config_to_phone_prepare` and `conffin_sent` (:354-355), not `isPhoneReady`/`bAckInfo`. nRF52 resets all of it inside both callbacks (see 2.6), so this asymmetry is ESP32-only.
- `g_ble_conn_handle` is not reset on disconnect (:309 init 0xFFFF, set :356). Guarded by `deviceConnected` in `esp32_write_ble` (:2098) and `esp32_ble_mtu` (:2122); `pServer->disconnect(g_ble_conn_handle)` at :3283 only runs under `deviceConnected`. Harmless today.
- `ble_busy_flag` (src/phone_commands.cpp:38) is set/cleared inside the same function call (:125-158, :175-204), single task, cannot outlive a disconnect.
- Rings (`phoneRing`, `phoneComRing`, drain state `s_phoneDrain`/`s_phoneComDrain` phone_commands.cpp:60) are NOT flushed on disconnect (no bf_reset anywhere). `addBLEComToOutBuffer` refuses pushes while not connected (loop_functions.cpp:733) but frames queued before a drop stay and go to the next central ahead of the new config burst; `mhPhoneListStart()` restarts the MH snapshot on each hello (esp32_main.cpp:3359). Whether stale frames matter is an open question (O2).
- The "connect flood"/ring fix of PR #1147 (b96cc510) is about ordering at connect (MHeard burst overwrote config frames in the com ring), not reconnect. The ring is byte-FIFO now (phoneComRing sized for the 12x246 B burst, loop_functions.cpp:554).
- Writes from the phone go through `bleQueue` (depth 5, esp32_main.cpp:295-303, onWrite :449-458, drop on full), drained in the loop (:3318-3322); not cleared on disconnect.
  1.10 Where `deviceConnected` / `g_ble_uart_is_connected` gate behaviour: message delivery and config burst only when `isPhoneReady==1` (phone_commands.cpp:127,177; loop_functions.cpp:5088,5119; udp_functions.cpp:1054); T-Deck BT icon (src/t-deck/lv_obj_functions.cpp:2302,2375); `addBLEComToOutBuffer` (loop_functions.cpp:733); AT/at_cmd.h macros. A stale TRUE would only block a next connection through the MAX_CONNECTIONS=1 limit (stack-level, not flag-level): nothing in firmware refuses a connect. A connect cannot be blocked by `deviceConnected`; `onConnect` just overwrites it.
  1.11 Other adv control: nothing in src stops or deinits advertising except the TM-11 bench flag `BENCH_BLE_ADV_LATE` (esp32_main.cpp:1985-1990, :2181-2183). `DISABLE_BLE` removes the whole stack (commit 9d8cbdbb). No watchdog "advertising still running?" check exists: no call to `isAdvertising()` anywhere in src.

### 2. nRF52 (Bluefruit, Adafruit nRF52 framework in ~/.platformio/packages/framework-arduinoadafruitnrf52, libs/Bluefruit52Lib)

2.1 All BLE in src/nrf52/nrf52_ble.cpp (494 lines). `Bluefruit.begin(1, 0)` = one peripheral link (:102); `configPrphBandwidth(BANDWIDTH_MAX)`, `configPrphConn(250, EVENT_LENGTH_MIN, 16, 16)` (:94-99).
2.2 Advertising: `restartOnDisconnect(true)` (:185), `setInterval(32, 244)` (20 ms fast, 152.5 ms slow), `setFastTimeout(15)` (:186-187), then `restart_advertising(0)` -> `Bluefruit.Advertising.start(0)` = advertise forever (:188-201). Lib restarts in BLE_GAP_EVT_DISCONNECTED with `start(_stop_timeout)` = 0, if no other peripheral link (BLEAdvertising.cpp:437-447, libs path above). Advert content: flags LE-only general disc, settings service UUID (`sett_service`, 0xF0A1 settings characteristic, NOT the NUS UUID), name, TX power (:171-174); scan response: name (:168). The NUS UUID is therefore not in the nRF52 advert (differs from ESP32 long mode).
2.3 Callbacks: `setConnectCallback(connect_callback)` / `setDisconnectCallback(disconnect_callback)` (:133-134); bodies :225-262 (disconnect_callback :254).
2.4 Connection parameters: firmware never calls `Bluefruit.Periph.setConnInterval/setConnSupervisionTimeout`; lib default PPCP is 20-30 ms interval, latency 0, 2 s supervision timeout (bluefruit_common.h:49-56). The phone (central) decides; the node does not request an update. Platform asymmetry: ESP32 requests 4 s, nRF52 keeps the 2 s lib default and requests nothing.
2.5 Bonding/PIN: `Bluefruit.Security.setPIN(PAIRING_PIN)` with `PAIRING_PIN "000000"` (nrf52_ble.cpp:105; src/configuration_global.h:571). The permission lines `g_ble_uart.setPermission(SECMODE_ENC_WITH_MITM...)` are commented out (:158, "KBC 28.04.2025"), so no characteristic requires encryption: no pairing happens unless the phone asks; if it does, the static PIN 000000 (not `bt_code`) applies. Real PIN protection is the same app-layer SHA-256 hello as ESP32. Lib default bonding behaviour is used (Bluefruit persists bonds in its own flash store when a phone does pair); not exercised by the firmware.
2.6 State on disconnect: `disconnect_callback` resets `g_ble_uart_is_connected`, `isPhoneReady`, `bAckInfo`, `config_to_phone_prepare`, `conffin_sent`, TX power 0 (:254-262); `connect_callback` (:225-247) resets the same set and sets TX power 4 and `last_mtu`. No race like 1.9 (note: runs in the Bluefruit Ada callback task, variables not volatile). Auth failure disconnect: `nrf52BleServiceDisconnect()` called from nrf52loop (nrf52_main.cpp:1756-1757, impl nrf52_ble.cpp:343-350). Rings not flushed here either.
2.7 `stop_advertising()` (:209-219, used by deep sleep nrf52_sleep.cpp:58) is the only place advertising is stopped.

### 3. Disconnect reasons

3.1 ESP32: reason is always printed, unconditional `Serial.printf("BLE disconnected. Reason: 0x%04x\n", reason)` (esp32_main.cpp:385). NimBLE passes 0x200 + HCI code: 0x208 supervision timeout, 0x213 remote user terminated, 0x216 local host terminated, 0x23E failed to establish (decoded by `bleReasonStr` :332-343, which covers 0x208/0x213/0x216/0x222/0x23B/0x23E). With `--bledebug on` (bBLEDEBUG) also `[BLE ];disconnect;ms;..;reason;..;text;..;dur;..;wifi;..;msys;..` (:387-392) plus connect/connparams/mtu lines. These Serial.printf calls run in the NimBLE host task and the debug line is >64 B (Print::printf mallocs, cf. N-18 heap lesson); keep new logging short or use `Serial.write`.
3.2 Not logged on ESP32: failed connection attempts (lib-internal, `Connection failed` only via NIMBLE_LOG at lib log level), advertising restart success/failure (lib ignores the return value, firmware cannot see it), count of reconnects. Addable: counters in onConnect/onDisconnect (e.g. consecutive-failures, last reason in `--info`), `NimBLEAdvertising::setAdvertisingCompleteCallback`, and a periodic `NimBLEDevice::getAdvertising()->isAdvertising()` self-check in esp32loop when `!deviceConnected`.
3.3 nRF52: `disconnect_callback(uint16_t, uint8_t reason)` receives the HCI reason but casts it away `(void)reason` (nrf52_ble.cpp:256-257) and logs only the static text via `DEBUG_MSG("BLE","Disconnected")` (compiled out when DO_DEBUG 0, see memory debug-msg-compiles-away). The Bluefruit lib's own `dbg_hci_str` log is off unless CFG_DEBUG. Add: print reason (0x08/0x13/0x16/0x3E) with a `Serial.printf` / `printfdeb` in `disconnect_callback`, mirror the ESP32 `[BLE ];disconnect;ms;..;reason;0x%04x` line (use 0x200+reason form or the raw HCI code, pick one and document it; ESP32 prints 0x2xx).

### 5. App side (APP=~/WebDev/Meshcom-MobileApp, Ionic/Capacitor, `@capacitor-community/bluetooth-le` 8.3.0, HEAD 0e10286 "App release 4.29", 2026-10-01)

5.1 The app has a reconnect implementation, switched off. src/pages/Connect.tsx: `onDisconnect` (:~895-960) on a non-manual disconnect would set `doReconnect`, write a recon state to the DB and call `reconnectBLE(deviceId)` (:975), but the whole block is commented out under "RECONNECT DISABLED !!!!!" (:908-931); the second trigger on app-resume (:285-296) is also commented out. `reconnectBLE` polls with `setInterval(recon_time)`, runs a 5 s `getScan()` each tick and `connDev(devID)` when the node shows up (:975-1030); `handleReconActive` is the "stop reconnect" button (:1045). 5.2 Connect path (Connect.tsx:595-640): Android waits `BLE_RECONNECT_DELAY = 2500` ms after the last disconnect (:68, :606-612), does a pre-connect `BleClient.disconnect`, then `BleClient.connect(devID, onDisconnect, {timeout: 15000})`. The plugin's Android `connectGatt(context, autoConnect=false, ...)` is hard-coded (node_modules/@capacitor-community/bluetooth-le/android/.../Device.kt:354-372): no autoConnect(true) anywhere in the app or plugin config. No Android foreground service found in android/app/src/main (grep "foreground": only icon xml hits), the code comment itself says iOS cannot scan in background without a service UUID filter and Android needs a foreground service. So: auto-reconnect, if wanted, must be either (a) foreground-only scan+connect loop (re-enable existing code, add backoff), (b) Android autoConnect(true) via plugin patch/fork (kernel-managed, works in background, needs a stable address -> public address OK), (c) iOS: connect-pending to a known peripheral UUID (CoreBluetooth keeps `connect` pending indefinitely; plugin timeout 15 s defeats this), plus iOS state restoration.

## Open questions for the operator

O1. Scope: is the deliverable firmware hardening plus a concept for the app (app lives in a separate repo, ~/WebDev/Meshcom-MobileApp, release 4.29 by a different maintainer), or also an app patch? The app already has a disabled reconnect loop; who decided to disable it and why (iOS/Android background limits per the code comment)?
O2. On ESP32, should ring/drain state and `bleQueue` be flushed on disconnect, or is "deliver stale frames to the next connect" intended (it hides lost frames from a phone that dropped mid-burst, but also delivers old traffic)?
O3. Bonding: stay at no-bond (N-07 WONTFIX, app fleet would break)? Without a bond the phone cannot use resolvable-private-address style reconnects; the node uses a public address so connect-by-address works anyway. Confirm nothing in #1191 asks for bonding.
O4. nRF52 connection parameters: leave at lib defaults (2 s supervision) or mirror the ESP32 4 s request (`Bluefruit.Periph.setConnSupervisionTimeout`)? Needs a RAK bench with an iOS phone; only the operator's phones can show it.
O5. Short vs long advert on ESP32 (`bBLElong` default off): should the NUS UUID always be in the advert/scan response for app-side filtered scanning (iOS background)? Costs adv bytes: the short mode exists because of the 31 B limit with long call signs (name cut at 26).
O6. Is a diagnostic-only first step wanted (reason logging nRF52, reconnect counters in `--info`, advertising self-check) before any behaviour change, given the field symptom is not reproduced on a bench (no "advertising stopped" case found in source)?
O7. Should the paper cover the fast-reconnect race window (disconnect -> advert resume is 0 ms in firmware but the supervision timeout of 4 s on a silent phone loss keeps the node unconnectable)? Option: a shorter timeout is rejected by iOS (dbd5db9c); alternative: firmware-initiated `disconnect` when the app-layer heartbeat (`TimeSyncManager` interval in the app) goes silent.
