# PR-Entwurf: fix(wifi): softAP auf einem Knoten ohne gespeicherte SSID starten

> **Status: ENTWURF** (Stand 2026-10-03, Basis `upstream/dev` = `e1e2acea`, Fix auf
> fork-dev als `42dbf03a`, Defekt-Katalog N-36). Ziel-Branch: icssw-org **DEV**.

## Titelvorschlag

`fix(wifi): softAP auch ohne gespeicherte SSID starten (frischer ESP32-Knoten)`

## Kurzfassung

`startNetwork()` brach bei leerer SSID oder `"none"` ab, **bevor** der `bWIFIAP`-Zweig
erreicht wurde. Ein frisch geflashter oder gelöschter ESP32-Knoten hat `node_ssid = "none"`;
damit kam `WiFi.softAP()` weder beim Erstboot noch nach `--wifiap on` jemals zur Ausführung.
Das Display zeigte `AP : <call>` ohne IP, auf Sendung war nichts. Im AP-Modus wird die SSID
gar nicht benutzt. Die Prüfung gilt jetzt nur noch für den STA-Modus.

Umfang: **2 Dateien in `src/`, +29 / −1**, eine Verhaltensänderung, ausschließlich auf dem
Pfad „kein SSID gespeichert **und** AP-Modus gewünscht".

---

## Problem

Reproduktion (Heltec V3, NVS gelöscht, Firmware 4.40a):

1. Frischen oder gelöschten ESP32-Knoten starten. `node_ssid` und `node_pwd` stehen auf
   `"none"` (`src/esp32/esp32_flash.cpp:362-363`), das Rufzeichen ist die Werkseinstellung
   (`XX0XXX-00`), `isNodeUnconfigured()` ist wahr und der Start setzt `bWIFIAP = true`
   (`src/esp32/esp32_main.cpp:1099-1101`).
2. Erwartet: der Knoten spannt den softAP mit dem Rufzeichen als SSID auf
   (`WiFi.softAP(meshcom_settings.node_call)`, `src/udp_functions.cpp:650`; Werksname also
   `XX0XXX-00`, nach `--setcall DK5EN-1` entsprechend `DK5EN-1`) und ist auf `192.168.4.1`
   erreichbar.
3. Beobachtet: Display `AP : XX0XXX-00` ohne IP, im Log
   `[WIFI]...no connection possible`, kein AP in der Luft. Dasselbe nach `--wifiap on`.
   Erst ein beliebiges `--setssid` löst es: der Operator muss eine SSID setzen, die der
   AP-Modus gar nicht verwendet.

Betroffen ist genau der Inbetriebnahme-Fall, in dem der AP der einzige Weg zur
Web-Konfiguration ist.

## Ursache

Die Prüfung in `startNetwork()` (`src/udp_functions.cpp`) stand vor dem `bWIFIAP`-Zweig.
Stand vor dem Fix (Parent von `42dbf03a`, `src/udp_functions.cpp:625`):

```cpp
if(meshcom_settings.node_ssid[0] == 0x00 || is_equ(meshcom_settings.node_ssid, "none"))
{
  return false;
}
```

Der `bWIFIAP`-Zweig mit `WiFi.softAP()` folgt erst danach (vor dem Fix Zeile 636). Die
Prüfung wurde mit `ed4ed3bba` (v4.35p, bereits in `upstream/dev`) eingeführt und war nur
für STA gemeint („`--webserver on` verlangt eine SSID"); sie bremste aber auch den AP aus.

Gegenprobe: der STA-Zweig besitzt schon eine eigene, spätere `"none"`-Prüfung
(`[WIFI]...ST no ssid<...> not connected`, nach dem Fix `src/udp_functions.cpp:664-668`).
Safeboot (`src/safeboot/main.cpp`) hatte die Logik bereits richtig.

## Änderung

Hunks von `git show 42dbf03a -- src` (nur `src/`):

**1. Neue Datei `src/wifi_start_gate.h`** (`@@ -0,0 +1,27 @@`)
Header-only, Arduino-frei, ein Prädikat:

```cpp
static inline bool wifiSsidMissingBlocksStart(bool apMode, const char *ssid)
{
    if(apMode)
        return false;

    return ssid == NULL || ssid[0] == 0x00 || strcmp(ssid, "none") == 0;
}
```

- Im AP-Modus blockiert eine fehlende SSID **nie**.
- Im STA-Modus blockiert sie bei `NULL`, leerer SSID und exakt `"none"` — dieselbe
  Semantik wie zuvor (`is_equ()` vergleicht ebenfalls exakt; der Test hält fest, dass
  `"NONE"` eine gültige SSID ist).
- Eigene Datei, damit das Prädikat ohne Arduino-Header im Host-Test linkt.

**2. `src/udp_functions.cpp`, Hunk `@@ -26,6 +26,7 @@`**
`#include "wifi_start_gate.h"` hinter `#include "setlog_lines.h"` (neue Zeile 29).

**3. `src/udp_functions.cpp`, Hunk `@@ -622,7 +623,7 @@` (`startNetwork()`)**
Zeile 626 neu (625 alt):

```diff
-  if(meshcom_settings.node_ssid[0] == 0x00 || is_equ(meshcom_settings.node_ssid, "none"))
+  if(wifiSsidMissingBlocksStart(bWIFIAP, meshcom_settings.node_ssid))
```

Der Aufruf bleibt an derselben Stelle (vor `wifiInitOnce()`), geändert ist nur die
Bedingung: sie ist jetzt `bWIFIAP`-bewusst. Der Kontrollfluss dahinter ist unverändert.

## Test

Neue native Testsuite `test/test_wifi_start_gate/test_wifi_start_gate.cpp`, **8 Fälle**
(Aufruf: `pio test -e native -f test_wifi_start_gate`):

| Modus | Eingabe                                 | Erwartung       |
| ----- | --------------------------------------- | --------------- |
| AP    | `"none"` (Regressionsfall)              | blockiert nicht |
| AP    | `""`                                    | blockiert nicht |
| AP    | `NULL`                                  | blockiert nicht |
| STA   | `"none"`                                | blockiert       |
| STA   | `""`                                    | blockiert       |
| STA   | `NULL`                                  | blockiert       |
| STA   | gesetzte SSID                           | blockiert nicht |
| STA   | `"NONE"` (Großschreibung ist eine SSID) | blockiert nicht |

Die drei AP-Fälle bilden den Fehler ab (das alte Gate hätte in allen dreien geblockt), die
fünf STA-Fälle sichern, dass der STA-Pfad unverändert streng bleibt.

Hardware (Heltec V3, DK5EN-1, NVS gelöscht): Firmware 4.40a meldet `WIFI-AP on` mit
`[WIFI]...no connection possible` ohne IP. Mit dem Fix: `[WIFI]...AP mode ssid<XX0XXX-00>
connected`, IP `192.168.4.1`; nach `--setcall DK5EN-1` und `--wifiap on` ist der AP
`DK5EN-1` auf `192.168.4.1` erreichbar.

## Risiko

Gering, weil nur eine Bedingung enger wird:

- **STA-Modus** (`bWIFIAP == false`): Verhalten bit-identisch (gleiche drei Bedingungen).
- **AP-Modus ohne SSID** (der Fehlerfall): läuft jetzt in den bestehenden `bWIFIAP`-Zweig,
  der sonst mit gesetzter SSID schon immer lief. Kein neuer Code im Zweig selbst.
- Aufrufer von `startNetwork()`: Hauptschleife und Watchdog-Funk-Reset
  (`src/esp32/esp32_main.cpp:2011, 3170, 4032`), `--wifi on` und Display-Schalter auf dem
  T-Deck (`src/command_functions.cpp:5063`, `src/t-deck/event_functions.cpp:290`). Der
  T-Deck-Gate `node_wifion` greift weiterhin **vor** dem geänderten Check. Ein Aufrufer,
  der im AP-Modus ohne SSID bisher still `false` bekam, startet jetzt den AP und bekommt
  `true`; das ist das gewünschte Verhalten.
- Ethernet-Pfad (RAK4631, `RAK13800_W5100S`) und Safeboot sind nicht berührt.
- Flash/RAM: ein `static inline`-Prädikat ersetzt `is_equ()` an einer Stelle,
  vernachlässigbar.
