7. Assessment

  • Not spoofing, not an attack. Position, client string, server hopping and the chat are all consistent with one phone in Zhanjiang. The aprs.fi position is correct and there is no contradiction with the message reaching Germany: it travelled APRS-IS to the MeshCom server to the mesh.
  • A client-side design flaw. APRSLocus CONNECT exposes a one-click "invite all online stations" that emits one APRS message per station, unthrottled, to a worldwide list. 3,394 messages in three seconds is far beyond anything the APRS-IS acceptable-use expectations tolerate, and a share of it was keyed on RF by igates in DL, OE, I and ON. The developer (BG7LZQ) is the right addressee for a complaint, not the tester.
  • For MeshCom. The message entered the mesh because DB0ED-99 is reachable from APRS-IS like any other APRS callsign. Any APRS-IS user worldwide can DM a MeshCom node; there is no filter on that bridge. If this is unwanted, the bridge is where to gate it (rate limit per source, or drop INVITE/JOIN_CONFIRM app-protocol traffic), not the node.
  • Group naming. CALL-Gn and the {NNNN_ message-id suffix are APRSLocus conventions. The earlier guess that this was aprs.fi's own group messaging was wrong; the OM says "APRSLocus group" himself, three times.
