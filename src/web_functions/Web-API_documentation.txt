============================================
Generic
============================================

The Web-API is following the REST (Representational State Transfer) paradigm.

Parameter names are considered to be lowercase (the backend at the node will convert them to lowercase).
Values are case-sensitive.

The Web-API is currently using the GET - request method. We may change that to POST later.
The Web-API is not yet finished or stable. We will add or change things. Please stay in touch with us if you rely on the Web-API. 

Page and JSON responses sent with the standard header (send_http_header) use chunked transfer encoding (Transfer-Encoding: chunked, no Content-Length), so a response that the node cut off is detectable as incomplete: the terminating zero-length chunk is missing and the HTTP client reports a network error.



============================================
Login (web password set)
============================================
When a web password is set (--webpwd), every request except the three below needs the session cookie
"mcs" that a successful login returns (WEB-AUTH-01, #1241). The password itself never travels:

	/?loginnonce					returns 32 hex chars (a one-time nonce, valid 30 s)
	/?login=<nonce>.<mac>			mac = HMAC-SHA256(key = password, msg = the 32 nonce chars), lowercase hex;
									200 + Set-Cookie: mcs=<token> on success, else 403 {"ok":false,"err":"..."}
	/?logout						drops the session of the request cookie

	Example (bash, openssl):
	n=$(curl -s -H 'X-MC: 1' http://<node>/?loginnonce)
	m=$(printf %s "$n" | openssl dgst -sha256 -hmac '<password>' | sed 's/.* //')
	curl -s -H 'X-MC: 1' -c jar "http://<node>/?login=$n.$m"; curl -s -b jar -H 'X-MC: 1' 'http://<node>/setparam/?onewire=on'

	The old /?nodepassword=<password> (plaintext) is refused with 403 {"ok":false,"err":"plaintext"}.
	Five failed logins within a minute block logins for 60 s. Sessions end after 4 h without a request.

============================================
Setting Parameters
============================================
To set a parameter to the node, use:

	NOTE (request guard): by default (build flag MC_WEB_GUARD=1; -D MC_WEB_GUARD=0 limits the guard to the
	remote-management endpoints /rm*, /?page=remote, /setparam/?rm= and /setparam/?rmstrict=) every
	state-changing request (/setparam, /callfunction, /?sendmessage,
	/?login=, /?logout and any POST) must carry
	the header "X-MC: 1" (the web page adds it itself), for example
	curl -H 'X-MC: 1' 'http://<node>/setparam/?onewire=on'. The callfunction actions upd*, otaupdate and
	reboot always need X-MC. Every request needs a Host that is an IP address, a single-label name or a
	*.local / *.fritz.box / *.lan / *.home.arpa / *.internal / *.speedport.ip / *.localdomain / *.home name
	(public FQDNs and reverse-proxy names are refused); otherwise, or without X-MC, the node answers 403.
	Typing a /setparam URL into the browser bar is refused for the same reason. The node sends no CORS headers.

	/setparam/?setcall=AB1CDE-12		Sets the nodes call-sign 
	/setparam/?onewiregpio=XX			Sets the GPIO to be used for the 1-Wire bus
	/setparam/?onewire=on|off			Enables 1-Wire at the configured GPIO
	/setparam/?buttongpio=XX			Sets the GPIO to be used for the User Button
	/setparam/?button=on|off			Enables a user-button at the configured GPIO
	/setparam/?setctry=XXX				Sets the country-specific LoRa Parameters (frequency, etc)
	/setparam/?txpower=XX				Sets the Power (in dBm) to be used by the nodes radio
	/setparam/?utcoffset=X.X			Sets the UTC offset (e.G. 1.5 or -3.0)
	/setparam/?maxv=X.XXX				Sets the maxV-parameter (ToDo: define what it is good for)
	/setparam/?display=on|off			Set permanent activated display to on or off
	/setparam/?small=on|off				Set if displayed content should be reduced to fit small displays
	/setparam/?volt=on|off				If set to on, battery SOC will be displayed as voltage instead of percentage
	/setparam/?mesh=on|off				Enables mesh / forwarding of received LoRa messages via radio
	/setparam/?blockcall=LIST|none	Blocked calls (same as --blockcall): comma list of up to 16 calls, CALL blocks all SSIDs, empty or none clears; invalid list = returncode 1, list unchanged; read-back (getparam) is the stored list
	/setparam/?gateway=on|off			Enables the gateway function
	/setparam/?rm=on|off				Enables the authenticated RM1 remote management by DM (same as --remotemgmt; stays inactive while no --passwd is set; read-back is the stored switch)
	/setparam/?rmstrict=on|off			RM brute-force protection (same as --rmstrictsecurity; default off): per-sender lockout, receiver rate limits and the sender budget only with on; read-back is the stored switch)
	/setparam/?aumode=off|prod|dev		(ESP32 only) Firmware auto update, one setting (off = --autoupdate off; prod|dev = --updchan prod|dev then --autoupdate auto, automatic install at 03:00-05:00 local; read-back is off|notify|prod|dev: "notify" while the console set notify mode, prod/dev only in automatic mode; any other value fails)
	/setparam/?mtu=1280..1500		Sets the MTU of the node's IP interface (same as --mtu; the web server advertises MSS = MTU - 40; default 1280 for HAMNET / VPN, 1500 for a plain LAN; all boards; read-back is the stored MTU, an out-of-range value fails)
	/setparam/?autoupdate=off|notify|auto	(ESP32 only) kept for compatibility, the setup page uses aumode: Firmware auto update mode (same as --autoupdate; auto installs at 03:00-05:00 local; read-back is the stored mode)
	/setparam/?updchan=prod|dev		(ESP32 only) kept for compatibility, the setup page uses aumode: Firmware update channel (same as --updchan; prod = icssw-org releases, dev = DK5EN releases; read-back is the stored channel)
	/setparam/?ethmtu=1280..1500		kept for compatibility, the setup page uses mtu: same as mtu
	/setparam/?setlat=XX.xxxxxx			Sets the latitude in decimal degrees (D.D°)
	/setparam/?setlon=XX.xxxxxx			Sets the longitude in decimal degrees (D.D°)
	/setparam/?setalt=XXX				Sets the altitude (in meters)
	/setparam/?gps=on|off				Enables using gps location
	/setparam/?track=on|off				Enables the display of SmartBeaconing
	/setparam/?setname=XXXX				Sets the desired APRS name
	/setparam/?atxt=XXXX				Sets the desired APRS text
	/setparam/?symid=C					Sets the desired APRS Symbol ID
	/setparam/?symcd=C					Sets the desired APRS Group ID
	/setparam/?angpio=XX				Sets the GPIO to be used for analog input
	/setparam/?checkanalog=on|off		Enables the analog measurement at the configured GPIO
	/setparam/?bmp=on|off				Enables BMP280 sensor support
	/setparam/?bme=on|off				Enables BME280 sensor support
	/setparam/?680=on|off				Enables BME680 sensor support
	/setparam/?811=on|off				Enables CMCU811 sensor support
	/setparam/?ina226=on|off			Enables INA226 sensor support
	/setparam/?softser=on|off			Enables the software Serial interface
	/setparam/?setgrc=XXX;XXX;XXX;XXX;XXX;XXX	Sets a List of six groups we wish to listen to.
	/setparam/?setssid=SSID				Sets the WiFi SSID
	/setparam/?setpwd=PWD				Sets the WiFi Password
	/setparam/?setownip=XXX.XXX.XXX.XXX sets an IP adress
	/setparam/?setownms=XXX.XXX.XXX.XXX sets a subnet mask
	/setparam/?setowngw=XXX.XXX.XXX.XXX sets a gateway
	/setparam/?extudpip=XXX.XXX.XXX.XXX sets an external UDP adress
	/setparam/?extudp=on|off 			Enables the usage of an ext. UDP adres
	/setparam/?kiss=on|off 				Enables the KISS/TCP interface (ESP32, port 8001)
	/setparam/?kisstx=on|off 			Allows transmit from connected KISS clients
	/setparam/?kissmeta=on|off 			Sends RSSI/SNR RxMeta frames (KISS port 1)
	/setparam/?kissauth=on|off 			Require HMAC-SHA256 auth on port 8001 (uses --passwd; standard KISS clients need auth off)
	/setparam/?manualcommand=COMMAND	Executes a Command. The commands parameters are usually seperated by space. You may need to percent-code spaces and other characters that otherwise are not allowed in a GET request


The Node will return a http return message.
The Status Code will be 200 if the parameter was set, 422 if the parameter could not be set (value was not accepted or parameter was not known).
The HTML Body will contain a JSON Object with a content body like: 

	{"returncode":0, "setcall":"AB1CDE-12"}
	
The returncodes are defined as:

	WS_RETURNCODE_OKAY 0			The parameter was set to the new value
	WS_RETURNCODE_FAIL 1			The parameter was NOT set to the new value
	WS_RETURNCODE_UNKNOWN 2			The parameter was not known
	
The JSON Object will also contain the parameter name that has been requested to set as well as the current value used by the node (or an empty string if the parameter was not found).
So if the parameter could be set to the new value, the returned value will contain the new value.
If the parameter could not be set (e.g. the value was not accepted) the returned value will contain the previous value that is still be used by the node.
This is to make sure your frontend stays synchron with the node.

	

============================================
Getting Parameters
============================================
To get parameter from the node, use:

	/getparam/?setcall

Replace "setcall" with any parameter name as listed in "Setting Parameters".

The Node will return a http return message.
The Status Code will be 200 if the Parameter was known and 422 if the parameter is not known.
The HTML Body will contain a JSON Object with a content body like: 

	{"returncode":0, "setcall":"AB1CDE-12"}

witch is the same as described in "Setting Parameters".




============================================
Calling Functions
============================================

A function is simply something that can be called but won't affect any setting or is considered to return any results.
We will return a http status code (200 or 422) depending on if the command was known or not

To call a function, use:

	/callfunction/?functionName=functionParameter

The function parameter is optional.
Not all functions require a parameter.


Functions available so far:

	/callfunction/?sendpos				The node will send its position or path 
	/callfunction/?reboot				The node will reboot 
	/callfunction/?otaupdate			The node will binto the OTA updater
	/callfunction/?updcheck			(ESP32 only) Check for a newer release now (same as --update check; 200 if the job started, 422 if busy or WiFi is down; read the result on the info page)
	/callfunction/?updinstall		(ESP32 only) Download and stage the newest release (same as --update install; 200 if the job started or the image is already staged, 422 otherwise)
	/callfunction/?updapply			(ESP32 only) Apply the staged image now (same as --update apply): the node reboots into Safeboot; 422 if nothing is staged

============================================
Remote Management of another node (RM1, all boards)
============================================

The setup page's "Remote management" card signs an authenticated RM1 command with the TARGET node's
password and sends it as a DM from this node (same protocol as the console; the target must have --remotemgmt on
and the same --passwd). Two dedicated endpoints serve it; they are NOT part of /setparam or /callfunction.
The DM may reach the target over LoRa or through the MeshCom server (a gateway node takes the command
straight from the server); the HMAC tag authenticates it on either path.

SECURITY: the target password travels once, in clear text, over plain HTTP between the browser and this
node. Do this only inside a LAN you trust, and set a web password on this node (--webpwd) so that nobody
else can reach these endpoints. This node uses the password only to derive a key (SHA-256), signs the
command, keeps the derived key in RAM for 10 minutes to verify the reply and never stores it. The node does
not log it: the request is not echoed to the debug console, the password is not part of any URL, and the
receive buffer is wiped after the call.


POST /rmsend

	Body (application/x-www-form-urlencoded, every value percent-coded):

		dst=AB1CDE-12&pw=<target password>&cmd=gps&args=on

	dst		the target call incl. SSID (upper case)
	pw		the target's password (1..14 characters)
	cmd		reboot | status | sendpos | sendtrack | gps | track | display | gateway | mesh | txpower | setout | sync
	args		on|off for gps/track/display/gateway/mesh, <n> dBm for txpower (<= board maximum),
			"<a0..b7> <on|off>" for setout, empty otherwise (sync counter: cmd=sync)
	pins, gpio	(GPIO-01) pins: empty = read, "<ow|an|wind> <0..48>" = assign (0 = board default, wind: off; an refuses 0); btn is
			read-only over RM (a restart applies it, a held pin can trigger the long-press deep sleep): "btn <n>" = err blocked;
			reply "ok ow=<n> btn=<n> an=<n> wind=<n>"; err refused | unsupported | blocked. gpio: empty = read, "<0..48> <on|off|in>" = switch a free GPIO
			(only with gpio control on at the node); reply "ok m=<0|1> o=<13 hex> i=<13 hex> l=<13 hex>" (bit n =
			GPIO n: held outputs, held inputs, level); err master | refused | unsupported

	Answer (JSON):	{"ok":true,"ctr":1760000123}		sent, ctr = the counter used (0 for sync)
			{"ok":false,"err":"<reason>"}		HTTP 422; reason: size | short | form | passwd | cmd | dst |
							busy (same target within 10 s) | ctr | store | send

	Slot form (a saved node, its key comes from the store; never a password):

		slot=<0..2>&cmd=<cmd>&args=<args>[&force=1][&call=<CALL>]

	call		optional guard (upper or lower case, folded like dst): the send is refused with err "slot"
			unless the saved slot currently holds exactly that call; nothing is sent, no counter is
			used. The page's "Run again" posts the row's call, so a slot re-saved in another tab cannot
			redirect a command to another node. Absent = no guard. call together with dst/pw = err
			"form"; an empty, over-long (> 9) or invalid call = err "call"; a duplicate = err "form".
	cmd		folded to lower case by the server.
	args		reach the wire exactly as typed (names keep their capitals, e.g. "Martin"); the command
			allowlist decides what is accepted, so "gps ON" is still refused ("cmd"): clients send
			on/off in lower case themselves.

	Body limit: 260 bytes (err "size" above). Worst case, every field fully %-coded: slot form with call
	about 220 bytes, dst form 258.

	A GET /rmsend is refused with 405: a password in a URL would be logged by browsers and proxies.

	The command is only SENT: the target's reply arrives later by DM and is verified by the node
	(see /rmstatus). A reply that fails the check is reported as unverified, never as success.


GET /rmstatus

	No parameters. Answer (JSON, printable ASCII only, < > & as \u escapes; never a key, a tag or a password):

	{"on":1,"pw":1,"ok":3,"rej":0,"lock":0,"lockS":0,"hwm":1760000100,
	 "log":[{"ago":42,"src":"DK5EN-1","ctr":1760000100,"cmd":"gps on","res":"gps=on"}],
	 "sent":[{"dst":"DK5EN-12","ctr":1760000123,"cmd":"status","ago":8,"rep":1,"ver":1,"reply":"ok v=4.40a up=12"}]}

	on, pw		RM switch of this node, a password is set (yes/no only)
	ok, rej		commands accepted / rejected since boot (all rejection reasons summed)
	lock, lockS	at least one sender (callsign-SSID) is locked out (3 rejects of that sender in 90 s) and the
			seconds until the last such lockout ends; other senders are not affected
	hwm		persisted counter high-water mark
	targets		(added to the document above) one object per distinct dst of the sent book plus the target
			of a command still waiting behind a sync: dst, locked, retry, canForce, cap, pending,
			chainErr, chainMsg (null or token / sentence)
	log		the last 5 commands THIS node executed, newest first: seconds ago, requester, counter, command, result
	sent		the whole book of commands this node SENT (up to 12), newest first, streamed one entry at a
			time (also fields st = queued|waiting|noanswer|ok|err|unverified and msg = one sentence): rep = some reply arrived, ver = its tag matched
			(verified); rep=1 with ver=0 is an UNVERIFIED reply, reply holds its raw (truncated) text


GET /pinstatus

	No parameters, GET only, read-only; behind the login like the pages. Answer (JSON, one line, user text escaped):

	{"led":{"fitted":1,"mode":"flash","busy":0,"rm":"","state":"flash"},
	 "chg":{"fitted":0,"mode":"off","eff":"off","rm":0},
	 "mcp":{"present":1,"pins":[{"id":"A0","n":"Relay","d":"out","l":1},{"id":"A1","n":"","d":"in","l":0}, ... 16 entries A0..A7, B0..B7]}}

	led		board LED: fitted, stored mode (off|flash|steady, as --board led), busy = OneWire owns the pad (T-Beam
			GPIO4) so the mode cannot run, rm = an RM1 "led" hold on the pad ("", on, flash), state = what the pad
			does now (busy -> off, else the hold, else the stored mode)
	chg		charge LED (AXP PMU boards): fitted, console mode (auto|off), effective mode (auto|on|off, RM1 "chgled"
			override included), rm = override active
	mcp		present = an MCP23017 answered at boot; pins is empty when it is not. d = in|out, l = level 0|1,
			n = pin name (<= 15 bytes; valid UTF-8 as it is, other bytes read as Latin-1)

	Cached state only, no I2C access in the request: an output level is the commanded one (the chip is written from it),
	an input level is the last sample of the 5 s refresh. The Pins page polls it every 5 s while it is shown and
	switches through /setparam/ (boardled=off|flash|steady, mcpout<P>=on|off, mcpio<P>=in|out, mcpname<P>=text).
	mcpout<P> on a pin that is configured as input (or an invalid port) answers returncode 1 and changes nothing; the Pins page shows
	"The node refused the change." and re-reads the state.


GET /pinassign

	No parameters, GET only, read-only; behind the login like the pages. Answer (JSON, one line):

	{"chip":"esp32","fn":[
	 {"id":"ow","param":"onewiregpio","avail":1,"pin":0,"def":4,"eff":4,"on":1,"restart":0,"ok":"0x00000000ffffffff"},
	 {"id":"btn","param":"buttongpio", ...}, {"id":"an","param":"angpio", ...}, {"id":"wind","param":"windpin", ...}]}

	chip		esp32 | esp32s3 | nrf52840 | none
	fn		always four entries in this order: 1-Wire (ow), button (btn), analog (an), anemometer (wind)
	param		the /setparam/ name that writes the assignment (the Setup page uses the same)
	avail		0 = this build cannot change it (function not compiled in, or read-only on the board)
	pin		stored setting, 0 = board default (button: 99 = no button; analog: 99 = unset reads as 0)
	def		board default, 0 = no pin (the board has no default; the anemometer never has one)
	eff		pin in use, 0 = no pin (board has no default and none stored): the stored pin, or the default when the stored one is 0. The button reports the pin read
			at boot (a newly stored value counts after a restart), 0 when it is 99 = no button
	on		the function is switched on
	restart		1 = a change takes effect after a restart (button); 0 = applies at once (1-Wire, analog, anemometer)
	ok		64-bit mask as hex text: bit n set = the setter accepts pin n for this function now (pin policy, minus the pins
			the console setter refuses on its own). Bit 0 (= default/off) is set unless the setter refuses 0: not for the
			analog pin (takes 1..98), nor for 1-Wire on BOARD_RAK4630 (also refuses 1 and 2; that macro is set on every
			nRF52 build). The button's 99 = "no button" is not a bit: the setter always accepts it. The node's own answer
			to the setparam stays authoritative.

	Numbers are clamped to 0..255. The Pins page polls it with /pinstatus every 5 s while it is shown, refuses a pin whose bit is clear
	without asking the node, and shows "Refused by pin policy." when the node answers returncode 1 (HTTP 422).


GET /gpiostatus

	No parameters, GET only, read-only, node-local (no CORS); behind the login like the pages. Answer (JSON, one line, at most 1 KB):

	{"avail":1,"master":0,"pins":[{"pin":13,"own":"","dir":"-","lvl":-1},{"pin":4,"own":"ow","dir":"-","lvl":-1}]}

	avail		1 = the board offers free GPIOs and the build has gpio control (ESP32); 0 = nothing to show (nRF52: always
			{"avail":0,"master":0,"pins":[]})
	master		the gpio control master switch. It is console-only (--gpiocontrol on|off): there is no /setparam name for it
			and no web or RM path switches it on. With master 0 every switch is refused.
	pins		the pins the board lists as free, ascending
	own		"" = free to switch; else what claims the pin right now: ow, btn, an, wind (the enabled function) or led
			(board LED); such a pin has no switch
	dir		in | out = held by gpio control; "-" = untouched
	lvl		0 | 1 = level of a held pin; -1 = unknown (untouched pins are never read)

	Switch: /setparam/?gpio<N>=on|off|in|release (N = pin number). Needs the header X-MC: 1 (HTTP 403 without it). The answer
	is the setparam answer: returncode 0 / HTTP 200 when done, returncode 1 / HTTP 422 when refused (master off, pin not free,
	or a value other than on|off|in|release). Release of a pin gpio control does not hold changes nothing and answers 0.
	No other setparam value reaches gpio control: a value carrying a chained "--gpiocontrol" / "&&gpiocontrol" is always
	refused (403, even with X-MC), a chained "--gpio" / "&&gpio" in any value needs X-MC like the update commands.
	Levels live in RAM only: nothing is stored, after a reboot every pin is an untouched input. The Pins page shows the
	table ("Free GPIO") only when the board offers a free pin, polls /gpiostatus after /pinassign every 5 s and, with
	master 0, lists the rows read-only with the note "GPIO control is off (serial or telnet console: --gpiocontrol on).".
